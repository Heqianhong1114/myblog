【CTFHub】Web-HG泄露 Writeup

操作者：何芊宏 | 操作日期：2026.9.20 | 分类：CTF | 标签：CTFHub, Web, 信息泄露, Mercurial, CyberChef

1. 题目信息

  • 平台：CTFHub
  • 分类：Web - 信息泄露 / HG泄露
  • 题目名称：HG泄露
  • 提示：开发人员使用 Mercurial 进行版本控制并部署上线，导致 .hg 目录泄露。Flag 在服务端旧版本的源代码中，不太好使的情况下，试着手工解决。

2. 解题思路

Mercurial (HG) 的元数据保存在 .hg 目录中。主要思路是下载其存储的清单和变更日志文件，解压后提取出真实文件名。本题中，由于自动化工具在 Windows 环境执行失败，且 WAF 对特定 .hg 路径请求返回 404，最终通过手工提取文件名，直接尝试在网站根目录访问该文件获取了 Flag。

3. 操作步骤

第一步：前期探测与工具尝试

尝试运行 dvcs-ripper 中的 rip-hg.pl，在 Git Bash 中报错 cannot find hg（因为本机没装 Mercurial 软件）。按照题目提示转向手工。

在浏览器直接访问 /.hg/requires，成功下载并看到 revlogv1 等信息，确认漏洞存在。

第二步：下载核心历史数据文件

手工下载了以下两个关键文件到本地：

  • /.hg/store/00manifest.i（记录文件清单）
  • /.hg/store/00changelog.i（记录提交日志）

此时尝试直接访问 /.hg/store/data/flag.txt.i 等路径，返回 404 Not Found。

第三步：CyberChef 手工解压与线索挖掘

Mercurial 的 .i 文件包含 64 字节的索引头，后面跟着 Zlib 压缩数据。使用在线工具 CyberChef，把下载的文件拖入 Input，配置配方：

Drop bytes (64) -> Zlib Inflate

解压 00changelog.i 后，看到提交日志里只有 50x.html、index.html 和 init。这说明目标文件并未正式提交。

但解压 00manifest.i 时，里面出现了一个未提交的文件名：flag_232234352.txt。

第四步：访问根目录获取 Flag（成功）

获取文件名后，尝试访问 /.hg/store/data/flag_232234352.txt.i 和 .d 后缀，全都报错 404。

分析发现，因为该文件在日志中没有提交记录，它可能只是一个被直接放在网站根目录下的普通文件。于是直接在浏览器地址栏输入：

http://challenge-c2740ff82eedba79.sandbox.ctfhub.com:10800/flag_232234352.txt

页面显示 Flag：

ctfhub{86667946a433108f96f3f212}

提交至 CTFHub，通关成功。

4. 踩坑记录与复盘

  • WAF 返回 404 的干扰：在访问 .hg 目录下包含敏感关键字的路径时，服务器返回 404 而不是 403，这是常见的拦截手段。碰到这种情况，不要一直死磕该路径。
  • 牢记先试根目录：当我们通过各种信息泄露手段（如版本控制、备份文件、目录遍历）获取到真实文件名后，第一反应应该是直接在网站根目录访问它（http://target/文件名）。如果 404，再按照版本控制的逻辑去深入挖掘。不要一开始就被复杂的目录结构限制住思维。

5. 知识总结

  • HG 泄露手工利用法：Mercurial 的文件存储在 .hg/store/00manifest.i（清单）和 00changelog.i（日志）中。可以通过下载它们，并采用“去头 64 字节 + Zlib 解压”的方式还原内容。
  • 未提交文件的存储特征：如果文件在 00changelog.i 里没有记录，但在 00manifest.i 里有名字，说明它是未被正式 commit 的游离文件，很大概率直接存在于 Web 工作区中。
  • 信息泄露的通用测试顺序：拿到文件名后，优先尝试根目录直接访问；失败后再尝试利用版本控制软件的命令或历史记录去恢复。
