【Pikachu】Web-XSS-反射型XSS(get) Writeup

操作者：何芊宏 | 操作日期：2026.9.27 | 分类：Pikachu | 标签：Pikachu, Web, XSS, 反射型XSS, 前端绕过

1. 题目信息

  • 平台：Pikachu 漏洞练习平台
  • 分类：Web - Cross-Site Scripting (XSS)
  • 题目名称：反射型xss(get)
  • 环境：使用 Burp Suite 自带浏览器访问靶场，通过 GET 参数传递 Payload。
  • 目标：在 GET 参数中注入恶意 JavaScript 代码，使浏览器执行并弹窗。

2. 解题思路与知识点

漏洞原理：

后端未对用户输入的 message 参数进行严格过滤和 HTML 实体转义，直接将其输出到了前端页面中。浏览器在渲染页面时，将用户输入的 <script> 标签识别为合法的 HTML 代码并执行。

Payload 成分解析：<script>alert(1)</script>
  • <script>：HTML 的脚本标签。浏览器解析到该标签时，会将其内部的内容视为可执行的客户端脚本（默认为 JavaScript）。
  • alert(1)：JavaScript 的内置函数。作用是弹出一个警告对话框，显示括号内的参数（这里是 1）。
  • </script>：脚本闭合标签，标志着 JavaScript 代码块的结束。

为什么选择 alert(1)？ 在渗透测试中，我们的首要任务是“证明代码被执行了”。alert(1) 是最简单、直观且无破坏性的证明方式（PoC）。在实际攻击场景中，攻击者会将其替换为更具危害的代码，例如 alert(document.cookie) 来窃取用户凭证。

前端校验绕过思路：

开发者通常会在前端 HTML 输入框中设置 maxlength 属性来限制输入长度。但这仅仅停留在客户端。攻击者可以通过 F12 审查元素修改 HTML 属性，或使用 Burp Suite 抓包修改请求参数来轻松绕过此限制。

3. 操作步骤

第一步：探测输出点

操作： 在输入框输入 Kobe，点击 submit。

回显结果： 页面显示 who is Kobe, i don't care!，且 URL 变为 ?message=Kobe&submit=submit。

获得信息： 确认输入内容通过 GET 参数 message 传递，并原样回显在页面中，且未经过滤。

第二步：尝试注入与绕过前端限制

操作： 尝试在输入框直接输入 Payload：<script>alert(1)</script>。

发现异常： 输入到 <script>alert(1)</sc 时输入框无法继续输入，被截断。

排查原因： 在输入框上右键，选择“检查 (Inspect)”，发现前端代码存在 maxlength="20" 属性限制。

绕过操作： 双击修改 maxlength="20" 为 maxlength="100"（或直接删除该属性），按回车。注意：不要刷新页面。

第三步：触发弹窗验证

操作： 回到输入框，重新输入完整的 Payload：<script>alert(1)</script>，点击 submit。

回显结果： 浏览器成功弹出 JavaScript 对话框，内容为 1。漏洞利用成功。

4. 踩坑记录与复盘

  • 坑1：前端长度限制导致 Payload 被截断。初次测试时，输入框存在 maxlength 属性，无法输入完整的 Payload。通过 F12 修改前端 HTML 源码成功绕过。
  • 坑2：URL 被自动编码。提交成功后，看到 URL 变成了 %3Cscript%3E，担心失效。实际上这是浏览器对 URL 中的特殊字符自动进行了 URL 编码，服务端接收时自动解码，不影响漏洞触发。

5. 知识总结

  • 反射型 XSS (GET) 特征： 非持久化。Payload 在 URL 中，需要诱导受害者点击恶意链接才能触发。页面回显是漏洞的关键。
  • 前端限制形同虚设： 渗透测试中，一切前端的限制（长度、验证码、JS 校验）都可以通过修改源码或抓包修改请求来绕过。真正的安全校验必须在服务端进行。
  • 防御建议： 服务端对所有的用户输入进行验证和过滤；在将数据输出到 HTML 页面前，使用 htmlspecialchars() 等函数进行 HTML 实体转义，将 < 转义为 &lt;，使浏览器将其视为纯文本。
