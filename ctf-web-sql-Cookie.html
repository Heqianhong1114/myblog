【CTFHub】Web-SQL注入Cookie注入 Writeup

操作者：何芊宏 | 操作日期：2026.9.24 | 分类：CTF | 标签：CTFHub, Web, SQL注入, Cookie注入, Burp Suite, 联合查询

1. 题目信息

  • 平台：CTFHub
  • 分类：Web - SQL注入 / Cookie注入
  • 题目名称：Cookie注入
  • 环境：通过 Open Browser 打开外部浏览器访问靶场环境。
  • 目标：输入点不在 URL 参数中，而是隐藏在 HTTP 请求头的 Cookie 字段里。需要利用 Burp Suite 拦截并修改 Cookie，最终获取 Flag。

2. 解题思路与知识点

本关核心考点：之前关卡的注入点都在 URL（如 ?id=1），而这关的输入点变成了 Cookie: id=1。由于浏览器地址栏无法直接修改 HTTP 请求头，因此必须使用 Burp Suite 进行抓包和修改。

工具思考：Burp Suite 的通用性与本关的特殊性
  • 以前的题目能不能用 BP 做？ 完全可以。BP 的核心作用是拦截 HTTP 请求。前几关的注入点在 URL 参数（?id=1），用 BP 的 Repeater 直接改参数，比在浏览器地址栏手打或等待 URL 编码效率更高。工具是通用的，核心在于你能否找准注入参数。
  • 这关的特殊性在哪里？ 特殊在注入点位置。URL 参数是浏览器可以直接交互的（地址栏），而 Cookie 是浏览器自动携带的 HTTP 请求头。如果不借助 BP 拦截，你无法在浏览器界面上修改它。因此，这关是“必须”而非“可以”使用 BP。

3. 使用 Burp Suite 进行手工注入的详细步骤

第一步：寻找 Cookie 中的注入点

操作： 打开 F12 -> 网络 -> 找到请求 -> 查看 Request Headers。

执行目的：寻找真正的注入点位置。

回显结果：发现 Cookie: id=1; hint=...。

获得信息：确认注入点位于 Cookie 的 id 参数中。同时页面给出了 hint 提示“输入点在这里，但不是id！”，这是一个干扰项，结合后续测试，真正的注入点其实就是 id。

第二步：用 Burp Suite 抓包并验证注入

Payload 1： Cookie: id=1 and 1=1

Payload 2： Cookie: id=1 and 1=2

执行目的：测试是否存在 SQL 注入漏洞。

BP操作过程：开启 BP 的 Intercept is on，由于当前页面没有输入框，直接在 BP 自带的浏览器界面按 F5 刷新页面。BP 拦截到请求后，右键 Send to Repeater。在 Repeater 的请求包中，将 Cookie 修改为以上 Payload，点击 Send。

回显结果：发送 and 1=1 时右侧 Response 正常显示 ID: 1 和 Data: ctfhub；发送 and 1=2 时页面数据消失或报错。

获得信息：确认存在 SQL 注入漏洞，且为整数型注入（无需引号闭合）。

第三步：寻找黄金回显点

Payload： Cookie: id=-1 union select 1,2

执行目的：利用不存在的 -1 使前半句查询为空，强制页面回显后半句 union select 的结果。

BP操作过程：在 Repeater 左侧修改 Cookie 参数为上述 Payload，点击 Send。

回显结果：右侧 Response 显示 ID: 1，Data: 2。

获得信息：确认第 1 列和第 2 列均为有效回显位，后续数据将放入第 2 列展示。

第四步：查询当前数据库名

Payload： Cookie: id=-1 union select 1,database()

执行目的：调用 MySQL 内置函数 database() 获取当前网站使用的数据库名。

BP操作过程：在 Repeater 左侧修改 Cookie 参数为上述 Payload，点击 Send。

回显结果：右侧 Response 显示 Data: sqli。

获得信息：确认当前数据库名为 sqli。

第五步：查询当前库的所有表名

Payload： Cookie: id=-1 union select 1,group_concat(table_name) from information_schema.tables where table_schema=database()

执行目的：查询系统库 information_schema.tables，获取当前库下所有的表名。

BP操作过程：在 Repeater 左侧修改 Cookie 参数为上述 Payload，点击 Send。

回显结果：右侧 Response 显示 Data: kbagombhtt,news。

获得信息：成功获取库中所有表名。发现目标表名为随机生成的字符串 kbagombhtt。另一个表 news 为干扰项。

第六步：查询指定表的字段名（列名）

Payload： Cookie: id=-1 union select 1,group_concat(column_name) from information_schema.columns where table_name='kbagombhtt'

执行目的：查询系统库 information_schema.columns，获取上一步发现的随机表 kbagombhtt 中所有的字段名。

BP操作过程：在 Repeater 左侧修改 Cookie 参数为上述 Payload，点击 Send。

回显结果：右侧 Response 显示 Data: kobohfmpce。

获得信息：确认该表的字段名为随机生成的字符串 kobohfmpce。

第七步：提取最终 Flag 数据

Payload： Cookie: id=-1 union select 1,kobohfmpce from kbagombhtt

执行目的：已知表名和字段名，直接从该表查询该字段的具体数据。

BP操作过程：在 Repeater 左侧修改 Cookie 参数为上述 Payload，点击 Send。

回显结果：右侧 Response 显示 Data: ctfhub{a7ce042c7e99950eaee8b4d5}。

获得信息：成功提取到 Flag，提交至 CTFHub，通关成功。

4. 踩坑记录与复盘

  • 坑1：浏览器无法直接修改 Cookie。发现注入点后，不要尝试在浏览器地址栏找输入框，必须借助 BP 的 Repeater 模块进行抓包和修改。
  • 坑2：题目提示的迷惑性。页面用 base64 编码给出了“输入点在这里，但不是id！”的提示。但经过实操，id 参数依然是有效的注入点。在 CTF 中，要用测试结果说话，不要被文字提示限制思路。
  • 坑3：环境脆弱。频繁的 BP 请求会导致靶场环境卡死。如果发送 Payload 后无响应或报错，立刻停止并销毁环境，重新开启，把新 URL 替换到 BP 中重新抓包。

5. 知识总结

  • Cookie 注入的本质：依然是 SQL 注入，只是注入点从 URL 参数转移到了 HTTP 请求头中。
  • 工具的意义：在遇到无法直接通过浏览器操作的数据包（如 Cookie、User-Agent、Referer）时，BP 是必备的抓包和重放工具。而前几关虽然不需要 BP 也能通关，但掌握 BP 后，能极大提升做题和实战的效率，它是未来安全路上最常用的兵器。
  • 脱库流程的一致性：无论注入点在哪里，脱库的底层逻辑（查库 -> 查表 -> 查字段 -> 数据）和 information_schema 系统库的利用方式，都是完全一致的。
