【Pikachu】Web-XSS-存储型XSS Writeup

操作者：何芊宏 | 操作日期：2026.9.27 | 分类：Pikachu | 标签：Pikachu, Web, XSS, 存储型XSS, 持久化

1. 题目信息

  • 平台：Pikachu 漏洞练习平台
  • 分类：Web - Cross-Site Scripting (XSS)
  • 题目名称：存储型XSS
  • 目标：在留言板中提交恶意 JavaScript 代码，验证该代码是否被服务器存储，并在每次页面刷新时触发执行。

2. 解题思路与知识点

漏洞原理：

存储型 XSS 是三种 XSS 中危害最大的一种。攻击者将恶意代码提交至服务器，服务器未经过滤直接将其存入数据库。当其他用户（如管理员）访问该页面时，服务器从数据库读取并输出这段代码，导致恶意脚本在受害者浏览器中执行。

存储型与 GET/POST 的关系：
  • GET/POST 只是传输方式：就像快递员，一个把包裹贴在车上(GET)，一个把包裹放进车厢(POST)。
  • 存储型是持久化机制：无论用 GET 还是 POST，只要服务器把数据存进了数据库，就是存储型。
  • 验证特性：反射型需要点击链接触发，存储型只需正常访问页面即可触发，且每次访问都会执行。

3. 操作步骤

第一步：提交恶意 Payload

操作： 在留言板文本框中输入：<script>alert(1)</script>，点击 submit 提交（此时通过 POST 方法发送请求）。

第二步：验证持久化触发

现象一： 提交后页面刷新，浏览器立刻弹出对话框 127.0.0.1 显示 1。

现象二： 留意到留言列表区域并没有显示 <script> 文本，而是出现了“删除”按钮。这是因为浏览器将 Payload 当作 HTML 标签解析并执行了，因此不会渲染为可见文字。

现象三（持久化验证）： 按 F5 触发浏览器的“确认重新提交表单”提示框。点击“取消”后，直接在地址栏回车（相当于发送 GET 请求重新加载页面）。

结果： 页面加载时再次弹出 alert(1)。证明恶意代码已成功写入数据库，每次访问该页面都会自动触发。

4. 踩坑记录与复盘

  • 坑1：疑惑“留言内容为什么是空的？”首次提交后，发现文本没有显示在页面上，而只有一个删除按钮。经分析，这正是 XSS 成功执行的证明——浏览器解析到了 <script> 标签并触发了弹窗，自然就不会将其作为文本渲染。
  • 坑2：F5 刷新弹出“确认重新提交表单”。浏览器为了防重复提交而拦截。正确做法是点击取消，然后在地址栏回车，使用 GET 方式请求页面，验证是否能够触发持久化 XSS。

5. 知识总结

  • 存储型 XSS 的破坏力：常见于留言板、评论系统、用户资料处。攻击者可以通过存储型 XSS 窃取大量用户的 Cookie，甚至配合 CSRF 实现蠕虫传播。
  • 反射型 vs 存储型：反射型在 URL 中，需点击链接触发，非持久化；存储型在数据库中，正常访问即触发，持久化，杀伤力更大。
  • 防御建议：对用户提交的数据进行严格的过滤，在写入数据库前进行转义，在输出到前端时使用 HTML 实体编码（如 htmlspecialchars()）。
