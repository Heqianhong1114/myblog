【CTFHub】Web-SSRF 302跳转 Bypass Writeup

操作者：何芊宏 | 操作日期：2026.9.26 | 分类：CTF | 标签：CTFHub, Web, SSRF, 302跳转, URL Bypass

1. 题目信息

  • 平台：CTFHub
  • 分类：Web - SSRF / 302跳转 Bypass
  • 题目名称：302跳转 Bypass
  • 环境：浏览器直接访问。
  • 目标：利用 SSRF 漏洞，通过外部可控的 302 跳转服务，绕过服务器对内网 IP 的字符串检测，成功访问 127.0.0.1/flag.php 获取 Flag。

2. 解题思路与知识点

通俗理解：如何“借刀杀人”绕过门卫？

这道题的核心依然是“校验逻辑”与“请求逻辑”的脱节。我们可以把请求过程拆成两个角色来理解：

  • 后端校验代码（门卫）：只允许请求外网合法域名。如果你输入 127.0.0.1 或 localhost，它直接拦截。
  • 底层网络库（翻译官，如 cURL）：拥有“跟随 302 跳转”的默认行为。你让它去请求 A 页面，A 页面返回“302，去访问 B”，翻译官就会乖乖地转去访问 B。

攻击思路：我们找一个外部的、可控的 302 跳转服务（如 httpbin.org）。门卫一看是 httpbin.org，外网域名，放行！然后 cURL 发请求过去，收到 302 响应，自动跳转到我们预设的 http://127.0.0.1/flag.php，成功拿到 Flag。

比喻参考：综合了 Vaadata SSRF Cheat Sheet 与 HackTricks SSRF 指南中对“校验逻辑与解析逻辑不一致”的通俗化演绎。

实战中常见的绕过形式：
  • 利用公开 302 服务：http://httpbin.org/redirect-to?url=http://127.0.0.1/flag.php
  • 利用域名解析：http://127.0.0.1.nip.io，自动解析为 127.0.0.1
  • 利用 URL 编码：http://127.0.0.1%2Fflag.php，绕过前端过滤，后端解码后生效
  • 利用短网址服务：将 127.0.0.1 转换为短网址，隐蔽性更强，但容易被封禁
  • 自建 302 跳转：利用 Python 或 Nginx 在自己服务器上写一个 302 跳转脚本，配合内网穿透使用

3. 详细步骤

第一步：探测拦截规则

操作： 浏览器直接访问 ?url=http://127.0.0.1/flag.php。

回显结果：页面提示 hacker! Ban Intranet IP。

获得信息：确认后端使用了黑名单，禁用了“127”、“172”等内网 IP 字符串。

第二步：利用 302 跳转和 localhost 绕过检测

Payload： ?url=http://httpbin.org/redirect-to?url=http://localhost/flag.php

执行目的：让门卫看到外网合法域名 httpbin.org 放行，然后 cURL 收到 302 跳转指令，去访问内网 localhost（即 127.0.0.1）。

回显结果：页面直接返回 ctfhub{c4453cfa6980e26e932dccc0}。

获得信息：成功利用 302 跳转 + localhost 替换，绕过了 IP 黑名单检测。

4. 踩坑记录与复盘

  • 坑1：直接使用 127.0.0.1 被拦截。 后端会直接搜索 URL 中的“127”字符串，一旦发现就立即阻断。
  • 坑2：使用 URL 编码后依然被拦截。 把 127.0.0.1 进行 URL 编码 %31%32%37.0.0.1 之后，后端解码后发现依然是“127”，依然会拦截。
  • 坑3：绕过方案：使用 localhost。 localhost 在 Linux 中默认解析为 127.0.0.1，但字符串中不含“127”，完美绕过后端的关键字匹配。

5. 知识总结

  • SSRF + 302 绕过的本质： 校验逻辑只看“外部域名”，而底层请求库（cURL）会跟随 302 跳转，导致“放行的请求”最终打到了内网。
  • 防御建议： 在 SSRF 防护中，必须禁止请求库自动跟随 302 跳转，或者对跳转后的目标 URL 进行二次校验，否则所有基于 URL 白名单的校验都会形同虚设。
  • 实战思维： 在进行 SSRF 绕过时，要多关注 URL 标准的特性和底层库的默认行为，往往一个简单的字符替换（如 127.0.0.1 换成 localhost）就能绕过绝大多数粗粒度的防御。
