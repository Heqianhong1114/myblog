【Pikachu】Web-暴力破解-验证码绕过(on client) Writeup

操作者：何芊宏 | 操作日期：2026.9.26 | 分类：Pikachu | 标签：Pikachu, Web, 暴力破解, 前端绕过, Burp Suite

1. 题目信息

  • 平台：Pikachu 漏洞练习平台
  • 分类：Web - 暴力破解 (Burte Force)
  • 题目名称：验证码绕过 (on client)
  • 目标：页面依然有验证码，但验证码的校验逻辑仅存在于前端（浏览器端）。需要绕过前端拦截，直接向服务端发送请求进行爆破。

2. 解题思路与知识点

漏洞原理：

前端校验是极其脆弱的。开发者为了节省服务器资源，将验证码的比对写在了 JavaScript 中（如 if (input != code) {...}）。但在 HTTP 协议中，请求是可以被拦截和修改的。攻击者完全绕过浏览器直接构造请求，服务端因为根本没有校验 vcode 参数，会直接处理账号密码。

【核心】第三关(on client)与第四关(token防爆破)的区分与判断方法：
  • 特征对比：
    • 验证码绕过(on client)：验证码字符串由前端 JS 动态生成或写死，服务端不校验 vcode。抓包后修改 vcode，服务端不会报错。
    • token防爆破？：服务端生成一次性 Token 隐藏在页面源码中，每次提交请求后，Token 都会刷新（用后即焚）。如果使用旧 Token 重放请求，服务端会直接拒绝（报错“非法请求”或“Token错误”）。
  • 判断方法（Repeater 测试法）：
    • 第一步：抓包并发送到 Repeater。
    • 第二步：修改验证码参数（改为 111111）。
    • 第三步：点击 Send 发送请求。
      > 若返回“密码错误”而非“验证码错误”，说明服务端无视了 vcode（前端绕过）。
      > 若返回“Token错误/验证失败”，说明服务端在下发 Token 后进行了严格校验（需利用 Burp 宏或 Python 脚本动态提取每次的 Token 进行爆破）。

3. 操作步骤

第一步：抓包与漏洞验证

操作： Burp 自带浏览器访问靶场 → 输入 admin / 123456 / 验证码 LTSNL → Burp 拦截到 POST 请求 → 右键 Send to Repeater。

Repeater测试： 在 Repeater 中，将 vcode=LTSNL 修改为 vcode=111111，点击 Send。观察 Response，发现服务器返回了“密码错误”的提示，并未拦截“验证码错误”。

源码分析： F12 查看前端代码，发现 JS 函数 validate() 内的逻辑：if (inputCode != code) { alert("验证码错误"); return false; }。

结论： 验证码拦截完全在前端执行，服务端未校验，直接爆破。

第二步：配置 Intruder 爆破

操作： 在 Repeater 中右键 -> Send to Intruder → 进入 Positions 标签页。

  • 点击 Clear §。
  • 只给 admin 和 123456 加 § 标记。
  • 关键点：将 vcode=111111 保留在请求体中（不加标记，保持固定）。
  • 攻击类型选择 Cluster bomb。

配置字典： 切换至 Payloads 标签页。Payload set 1（用户名）填入：admin, test, pikachu, root；Payload set 2（密码）填入：123456, abc123, 000000, password。

第三步：发起攻击与验证

操作： 点击 Start Attack，等待 16 个请求跑完。

回显结果： 观察 Length 列，发现请求 admin / 123456 的 Length 为 36559，其余均为 36584。双击该请求，查看 Response，搜索 success，发现 1 match，页面渲染显示 login success。

验证结果： 回到浏览器，输入 admin / 123456，成功登录，通关！

4. 踩坑记录与复盘

  • 坑1：在源码中搜不到验证码的值。最初在 F12 源码中直接搜索验证码 HJ6YQ，显示“未找到匹配项”。原因是因为验证码是由 JS 动态生成的（每次刷新页面重新生成），而不是写死在 HTML 中。此时无需纠结，直接通过抓包测试行为即可。
  • 坑2：被前端 JS 的表象迷惑。修改 vcode=111111 发送请求后，浏览器依然弹窗“验证码错误”。但这只是浏览器前端 JS 的弹窗，我们使用 Burp 直接发包，服务端依然正常处理了请求。这说明前端拦截在渗透测试中是不堪一击的。

5. 知识总结

  • 前端校验不可信：任何在客户端（浏览器）完成的校验（如 HTML、JavaScript）都可以被绕过。服务端必须对所有的客户端输入进行二次严格校验。
  • 实战爆破策略选择：面对验证码机制，第一步永远是抓包分析。通过在 Repeater 修改参数，判断服务端是否校验。若前端校验，直接爆破；若后端校验但可复用，使用固定验证码或自动化脚本；若后端动态 Token，则需要提取 Token 更新机制。
  • 修复建议：验证码必须在服务端生成和校验；每次校验后销毁，且必须与当前用户的 Session 绑定；禁止仅依赖前端 JavaScript 进行安全校验。
