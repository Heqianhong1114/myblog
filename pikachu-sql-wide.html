【Pikachu】Web-SQL-Inject 宽字节注入 Writeup

操作者：何芊宏 | 操作日期：2026.9.28 | 分类：Pikachu | 标签：Pikachu, Web, SQL注入, 宽字节注入, 源码审计, PHP8, Burp Suite

1. 题目信息

  • 平台：Pikachu 漏洞练习平台
  • 分类：Web - SQL-Inject
  • 题目名称：宽字节注入
  • 目标：理解宽字节注入原理，尝试利用 %df 吃掉转义符 \，绕过单引号过滤。

2. 解题思路与知识点

漏洞原理：

宽字节注入利用了数据库字符集编码的特性。当后端使用 GBK 等宽字节字符集时，若输入 %df（字节 0xdf）和转义符 \（字节 0x5c）相邻，MySQL 会将它们解析为一个合法的 GBK 汉字（如 %df%5c 对应“運”），从而“吃掉”反斜杠，使得原本被转义的单引号 ' 逃逸，成功闭合 SQL 语句。

工具选型与心路历程：
  • Python 脚本发送原始字节：由于浏览器地址栏会自动对 %df 进行二次编码，使用 Python 的 requests 库发送 bytes 对象是绕过 URL 编码陷阱的关键。
  • 源码审计发现致命逻辑：经过源码分析，发现 escape() 转义函数在 set character_set_client=gbk 之前执行，导致转义时使用的是默认的 UTF-8 字符集。
  • 环境差异与 PHP 8 机制：在 PHP 8 环境下，mysqli_real_escape_string 在 UTF-8 字符集下遇到 0xdf 这个非法字节会直接丢弃，导致 %df 无法“吃掉”反斜杠。这是本地环境与网络教程环境的根本差异。

3. 操作步骤

第一步：源码审计与关键逻辑分析

操作： 使用 VS Code 打开 sqli_widebyte.php 源码。

核心代码片段：

$name = escape($link,$_POST['name']);  // 1. 先执行转义（使用默认 utf8 字符集）
$query="select id,email from member where username='$name'";
$set = "set character_set_client=gbk";  // 2. 后设置 gbk 字符集（为时已晚）
execute($link,$set);
$result=mysqli_query($link, $query);

代码解析： escape() 函数在 set character_set_client=gbk 之前执行。这意味着在转义时，数据库使用的是默认的 UTF-8 字符集。在 UTF-8 下，%df 是一个无效字节，会被丢弃，而单引号 ' 会被成功转义成 \'。因此，%df 根本无法“吃掉”反斜杠，宽字节注入失败。

第二步：Python 脚本编写与测试

操作： 编写 Python 脚本，使用 bytes 对象发送原始 %df 字节，绕过 requests 的 URL 编码。

代码：

import requests

url = "http://127.0.0.1/pikachu/vul/sqli/sqli_widebyte.php"

def check_condition(condition):
    # 使用 bytes 对象发送原始 0xdf 字节和单引号
    payload_bytes = b"kobe\xdf' and " + condition.encode() + b" -- "
    data = {"name": payload_bytes, "submit": "查询"}
    r = requests.post(url, data=data)
    return "your uid:" in r.text

print("[*] 测试 1=1 ...")
if check_condition("1=1"):
    print("[+] 1=1 页面正常，宽字节注入存在！")
else:
    print("[-] 1=1 失败。")

print("[*] 测试 1=2 ...")
if not check_condition("1=2"):
    print("[+] 1=2 页面异常，漏洞确认！")
else:
    print("[-] 1=2 也正常，可能注入失败。")

回显结果： 1=1 失败，1=2 页面异常（显示不存在）。两者行为一致，证明注入失败。

第三步：Burp Suite 抓包尝试

操作： 很多师傅的 Writeup 提到，利用 Burp Suite 抓包并直接修改原始请求包，可以成功发送 %df 字节，从而绕过浏览器的 URL 编码。

Burp 中的原始 Payload：

name=kobe%df' and 1=1-- &submit=查询

回显结果： 依然失败，页面返回“您输入的username不存在，请重新输入！”。

原因分析： 即使通过 Burp 发送了原始的 %df 字节，但在 PHP 8 环境下，mysqli_real_escape_string 在处理转义时使用了 UTF-8 字符集。UTF-8 将 0xdf 视为非法字节并丢弃，导致后续的单引号被成功转义，宽字节注入无法利用。

第四步：阅读他人 Writeup 与最终结论

他人做法： 大多数成功的 Writeup 基于较早的 PHP 版本（如 PHP 5.6 或 7.0）。当时 mysqli_real_escape_string 对宽字节的处理逻辑与现在不同，使得 %df 能成功吃掉反斜杠。

结论： 由于靶场源码存在执行顺序错误（先转义后设字符集），加上 PHP 8 对非法字节的处理更加严格，导致这个关卡在本地 PHP 8 环境下无法利用。这并非攻击者技术问题，而是环境兼容性差异。

4. 踩坑记录与复盘

  • 坑1：URL 编码陷阱。 浏览器地址栏和 Python requests 库都会对 %df 进行二次编码，导致其失去原始字节含义。解决方案是使用 bytes 对象发送原始数据，或用 Burp Suite 拦截原始请求。
  • 坑2：靶场源码顺序错误。 escape() 在设置 GBK 字符集之前执行，导致转义时使用的是 UTF-8，%df 被丢弃，单引号被成功转义。这是靶场代码的逻辑 Bug。
  • 坑3：PHP 8 环境限制。 PHP 8 在 UTF-8 字符集下丢弃非法字节 0xdf，使得宽字节注入的核心物理条件无法成立。这是旧靶场在新环境下的兼容性问题。

5. 知识总结

  • 宽字节注入核心： 依赖 GBK 等宽字节字符集，利用 %df 和 \ 组合被解析为汉字，从而吃掉转义符。其成功前提是：数据库连接必须使用宽字节字符集。
  • 环境差异是渗透测试的常态： 面对旧靶场在新环境下的兼容性问题，应灵活分析源码，定位问题根因，而不是盲目怀疑自己的技术。
  • 防御建议： 统一使用 UTF-8 字符集，避免使用宽字节字符集；在转义前确保字符集设置正确；使用预编译语句（Prepared Statements）从根本上防御 SQL 注入。
