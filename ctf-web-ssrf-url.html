【CTFHub】Web-SSRF URL Bypass Writeup

操作者：何芊宏 | 操作日期：2026.9.26 | 分类：CTF | 标签：CTFHub, Web, SSRF, URL Bypass, 解析差异, @符号绕过

1. 题目信息

  • 平台：CTFHub
  • 分类：Web - SSRF / URL Bypass
  • 题目名称：URL Bypass
  • 环境：普通浏览器直接访问。
  • 目标：利用 URL 规范的解析差异，绕过服务端的白名单前缀校验，成功请求内网 127.0.0.1/flag.php 获取 Flag。

2. 解题思路与知识点

通俗理解：什么是“校验”与“实际请求”的脱节？

我们可以把服务器想象成一栋大楼的“前台”。老板规定：“凡是自称来自 A 公司（notfound.ctfhub.com）的人，都可以放行”。

这个时候，黑客伪造了一个名字：A公司@真正的黑客（127.0.0.1）。

  • 前台（后端校验代码）：只懂死记硬背，用 startswith("http://notfound.ctfhub.com") 检查字符串，一看名字以 A 公司开头，立刻放行。
  • 大楼导航员（cURL / 底层请求库）：懂标准的 URL 规范。它看到 @ 符号，知道 @ 前面的只是用户名（Userinfo），@ 后面的才是真正的目标主机。于是导航员直接把请求带到了真正的黑客面前（即内网 127.0.0.1）。

这种因“安全校验代码”和“实际发起请求的代码”对 URL 解析不一致产生的漏洞，正是 SSRF 中最经典的绕过手段之一。

URL 标准结构拆解：

一个完整的标准 URL 结构如下：

scheme://[userinfo@]host[:port]/path?query#fragment

对应到我们的 Payload http://notfound.ctfhub.com@127.0.0.1/flag.php：

  • scheme：http:// （协议）
  • userinfo：notfound.ctfhub.com （用户名，用于基础认证，这里只是伪装用的字符串）
  • @：分隔符，告诉解析器前面是用户信息，后面是主机信息
  • host：127.0.0.1 （真实访问的目标主机）
  • path：/flag.php （请求路径）

3. 详细步骤

第一步：环境探测与规则确认

操作： 开启题目后，浏览器直接访问靶场首页。

回显结果：页面提示 url must startwith "http://notfound.ctfhub.com"。

获得信息：确认后端代码使用了前缀白名单校验，符合我们预测的“校验与请求脱节”场景。

第二步：构造并发送绕过 Payload

Payload： ?url=http://notfound.ctfhub.com@127.0.0.1/flag.php

执行目的：利用 @ 符号，让前端字符检查通过，让后端实际请求打向内网本机。

回显结果：页面直接返回 ctfhub{65738b238e7c337b8fd29e55}。

获得信息：成功利用 URL 解析差异绕过了白名单校验。

4. 踩坑记录与复盘

  • 坑1：误以为这是单纯的字符串过滤。 如果只把 notfound.ctfhub.com 当作字面量拼凑（例如直接去修改 Host 头），可能无法成功。必须利用 URL 规范的语法特性（@ 符号），构造出在字符串上符合白名单、在协议解析上指向内网的畸形 URL。
  • 坑2：前端浏览器可能对 @ 编码。 在极少数情况下，浏览器会自动把 @ 编码为 %40 导致绕过失败。实战中遇到这种情况，通常会直接使用 Burp Suite 抓包，在请求行中修改原始参数，或者用 Python 脚本直接发送请求来确保 Payload 原样送达。

5. 知识总结

  • URL 解析差异（Parser Differential）： 不同的库（前端 JS、后端框架、cURL 等）对同一个 URL 字符串的理解可能存在差异。安全防御建议不要依赖简单的字符串匹配（startswith）来校验 URL，而应当使用标准的 URL 解析库解析出 host 字段后再进行白名单比对。
  • SSRF 常见绕过手段之 @ 符号： 利用 http://白名单域名@内网IP 的形式，直击“校验与请求脱节”的逻辑盲区。
