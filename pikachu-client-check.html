【Pikachu】Web-不安全的文件上传-client check Writeup

操作者：何芊宏 | 操作日期：2026.9.28 | 分类：Pikachu | 标签：Pikachu, Web, 文件上传, 前端绕过, Burp Suite, 代码执行

1. 题目信息

  • 平台：Pikachu 漏洞练习平台
  • 分类：Web - Unsafe Fileupload (客户端检查)
  • 题目名称：client check
  • 目标：绕过前端 JavaScript 扩展名校验，修改 HTTP 请求中的文件名与文件内容，将包含恶意代码的 PHP 文件上传至服务器并成功执行。

2. 解题思路与知识点

漏洞原理：

后端应用为了提升用户体验，会在前端使用 JavaScript 对文件扩展名进行校验，禁止用户上传非图片文件。但这种方式极易绕过，因为攻击者可以使用抓包工具（如 Burp Suite）拦截 HTTP 请求，在请求发出后、服务器接收前，将文件名和文件内容修改为恶意脚本。

“前端校验”与“后端校验”的区别：
  • 前端校验：运行在用户浏览器中，通过 JS 实现。仅能拦截普通用户的误操作，对攻击者无效。
  • 后端校验：运行在服务器端，通过 PHP 等语言实现。这才是真正的安全防线。如果后端校验也缺失，则造成任意文件上传漏洞。

3. 操作步骤

第一步：前端拦截演示与请求分析

操作： 使用 Burp 自带浏览器，尝试在文件选择框中选择并上传 shell.php。

回显： 浏览器弹出提示框“上传的文件不符合要求，请重新选择！”。

原理分析： 前端 JavaScript 在文件被提交前，检测到后缀名不是图片（如 .jpg, .png），直接阻断，HTTP POST 请求根本未发送。Burp Suite 无法拦截到任何数据。

第二步：绕过前端并使用 Burp 篡改上传请求

操作： 为了触发 POST 请求，在浏览器中先选择一个真实的图片文件（1.jpg）。打开 Burp Suite 开启代理拦截。

篡改请求： 点击“开始上传”后，Burp 成功拦截 POST 请求，找到 filename="1.jpg"，将其修改为 filename="shell.php"。

代码组成详细解释：

  • Content-Disposition: form-data; name="uploadfile"; filename="shell.php"：这是 HTTP 请求中的文件上传描述头。filename 的值会被后端解析为上传的文件名。后端如果只校验后缀，会被绕过。
  • Content-Type: image/jpeg：文件类型标识，本例中保持为图片类型，以降低被后端过滤的几率。

回显特征： 页面提示“文件上传成功”，并显示文件保存路径为：uploads/shell.php。

第三步：在 Burp 中替换请求体，植入 PHP 代码

发现新问题： 虽然文件上传成功，但直接访问 uploads/shell.php 只显示图片的二进制乱码。原因是文件内容依然是图片，不含 PHP 代码。

解决办法： 在 Burp 拦截到的 POST 请求中，直接替换请求体内容，并伪造文件名与文件类型。

Burp Suite 详细操作步骤与原理：

  1. 开启拦截： 在 Burp Suite 的 Proxy 面板中，确保 Intercept is on（拦截开启）。
    为什么： 让 Burp 作为浏览器与服务器之间的“中间人”，暂停 HTTP 请求的发送，以便我们修改数据包。
  2. 触发请求（伪装正常用户）： 回到浏览器，点击“选择文件”，选中真实的图片 1.jpg，点击“开始上传”。
    为什么： 前端 JavaScript 只校验扩展名。选择图片能通过前端校验，使得浏览器真正把带有文件数据的 POST 请求发出去。如果直接选 shell.php，请求会在浏览器本地被 JS 掐断，Burp 根本看不到。
  3. 拦截请求： 此时浏览器会卡住（转圈等待）。切回 Burp Suite，你会看到一个 POST /pikachu/vul/unsafeupload/clientcheck.php 请求。
    为什么： 这是真正的文件上传请求，包含了 HTTP 请求头和上传的文件内容。
  4. 篡改文件名（第一处修改）： 在请求头部分，找到 Content-Disposition: form-data; name="uploadfile"; filename="1.jpg"，将 filename="1.jpg" 修改为 filename="shell.php"。
    为什么： 后端代码通常通过获取 filename 参数来决定保存文件的名字。修改后缀名可以欺骗只检查后缀名的后端，让服务器把文件当作 PHP 脚本来保存。
  5. 篡改文件内容（第二处修改）： 在请求体（Body）中找到 Content-Type: image/jpeg 下方原有的图片二进制数据（乱码），将其全部删除。替换为 PHP 代码：<?php echo "pikachu_upload_success"; ?>。
    为什么： 仅仅改名字不够，如果文件内容依然是图片，服务器保存后的文件只是一张被改名为 php 的图片，内部没有 PHP 代码，无法被解析器执行。必须把内容替换成真正的 PHP 代码，并且保留 Content-Type: image/jpeg 以欺骗后端可能的文件类型检测（如 getimagesize）。
    代码结构解析： 请求体中 ------WebKitFormBoundary... 是分隔符，代表不同表单字段的边界。Content-Disposition 描述文件信息，空行之后的就是文件的实际内容。
  6. 放行请求与验证： 确认无误后，点击 Forward 放行请求。随后关闭 Intercept，防止页面其他请求被卡住。
    为什么： 放行使修改后的恶意请求真正发送给服务器。服务器接收后，将其保存为 PHP 文件，当浏览器访问时，PHP 解析器识别 <?php ... ?> 标签并执行 echo 语句。

回显特征： 页面提示“文件上传成功”。访问 uploads/shell.php，页面顶部成功执行 PHP 代码并输出 pikachu_upload_success，随后显示部分图片二进制残留的乱码。

4. 踩坑记录与复盘

  • 坑1：直接上传 PHP 文件导致 Burp 抓不到包。初次尝试在浏览器中直接选中 shell.php，因为前端 JS 报错“文件不符合要求”，请求被阻断，Burp 无法拦截到任何 POST 数据。
    解决办法：放弃直接在浏览器中上传恶意文件。改为在浏览器中选择合法图片，让请求顺利发出并被 Burp 拦截，随后在 Burp 的原始数据中直接将 filename="1.jpg" 篡改为 filename="shell.php"，成功绕过前端校验。
  • 坑2：仅修改文件名导致代码无法执行。初次仅修改了文件名，文件内容依然为 JPG 图片的二进制数据。访问该文件时，PHP 解析器找不到 <?php 标签，直接输出了图片乱码。
    解决办法：在 Burp 拦截器中，不仅需要修改文件名，还需要删除请求体中的二进制图片数据，将其替换为有效的 PHP 代码。这样生成的文件既保留了文件头（以绕过潜在的 getimagesize 检测），又包含了可执行的 PHP 代码，最终成功执行 echo 语句。

5. 知识总结

  • 漏洞本质：不安全的文件上传的本质是“信任边界失效”。前端校验不能作为安全防线，任何客户端的输入都是不可信的。
  • 防御措施：在服务端使用白名单校验文件扩展名（仅允许 .jpg, .png 等），同时对文件内容进行校验（使用 getimagesize() 检查文件头），限制上传目录的执行权限（禁止目录解析 PHP）。
  • 实战启发：遇到文件上传功能，首先应测试前端绕过（直传、抓包改后缀）。如果后端结合了文件头检查，则尝试制作图片马；如果后端还能解析二次渲染后的图片，则需结合文件包含漏洞来执行代码。
