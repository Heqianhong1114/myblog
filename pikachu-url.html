【Pikachu】Web-URL重定向漏洞 Writeup

操作者：何芊宏 | 操作日期：2026.10.1 | 分类：Pikachu | 标签：Pikachu, Web, URL重定向, Open Redirect

1. 题目信息

  • 平台：Pikachu 漏洞练习平台
  • 分类：Web - URL重定向 (URL Redirect)
  • 题目名称：不安全的URL跳转
  • 目标：利用后端未验证重定向 URL 的缺陷，构造恶意的 GET 请求，让服务器返回 302 重定向响应，将用户引导至任意外部网站（如钓鱼网站）。

2. 解题思路与知识点

漏洞原理：

不安全的 URL 跳转（Open Redirect）漏洞产生的原因在于，后端代码允许用户控制重定向的目标地址。当用户点击链接时，服务器会响应一个 302 状态码和 Location 头，告诉浏览器跳转到指定的 URL。如果后端未对该 URL 进行白名单校验，攻击者就可以构造指向恶意网站（如高仿钓鱼页面）的链接，利用用户对原域名的信任实施欺骗。

漏洞利用常见场景：
  • 钓鱼攻击：构造 http://trusted-site.com/redirect?url=http://evil-site.com，用户以为是在访问信任的站点，点击后却被跳转到伪造的登录页面。
  • XSS 结合：如果目标支持 javascript: 协议，可尝试构造 XSS 攻击。

3. 操作步骤

第一步：源码审计与漏洞点确认

操作： 使用 VS Code 打开源码文件 vul/urlredirect/urlredirect.php，审查重定向逻辑。

源码分析：

if(isset($_GET['url']) && $_GET['url'] != null){
    $url = $_GET['url'];
    if($url == 'i'){
        $html.="<p>好的，希望你能坚持做你自己！</p>";
    }else {
        header("location:{$url}");
    }
}

结论： 代码通过 GET 方式接收 url 参数，在第 22-24 行中，未经过滤直接将其拼接到 header("location:{$url}") 中。攻击者完全控制了重定向目标，存在 Open Redirect 漏洞。

第二步：构造恶意 Payload 并触发跳转

操作： 在浏览器地址栏输入以下 URL，尝试跳转到百度：

攻击 Payload：

http://127.0.0.1/pikachu/vul/urlredirect/urlredirect.php?url=http://www.baidu.com

回显特征： 浏览器地址栏瞬间跳转为 https://www.baidu.com，成功跳转至外部网站。

第三步：Payload 代码组成详细拆解

  • http://127.0.0.1/pikachu/vul/urlredirect/urlredirect.php：目标靶场接口地址。
  • ?：URL 参数起始符。
  • url=：后端接收的参数名。
  • http://www.baidu.com：攻击者控制的重定向目标。此处为百度首页，用于验证跳转是否成功。若为攻击载荷，可替换为精心构造的钓鱼网站地址。

后端执行过程： 后端接收到 url 参数，执行 header("Location: http://www.baidu.com");。服务器返回 302 状态码，浏览器根据 Location 头自动跳转到百度首页。

4. 踩坑记录与复盘

  • 坑1：前端点击无反应。初次尝试点击页面上“像春天的花一样的少年”等诗句，浏览器地址栏没有发生任何变化，无法正常触发跳转逻辑。
    原因排查： 页面上的诗句并未正确绑定携带 url 参数的超链接（<a> 标签），因此后端未收到跳转指令。
    解决办法： 放弃前端点击操作，直接通过审查后端源码找到注入参数 url，并手动构造 GET 请求进行访问。这证明了渗透测试中“源码审计”与“绕过前端限制”的重要性。

5. 知识总结

  • 漏洞本质：Open Redirect 漏洞的本质是“信任边界失效”。后端过度信任客户端提交的重定向目标参数，将其直接用于 HTTP 响应头，导致攻击者可利用原域名的信任度实施钓鱼攻击。
  • 防御措施：不要信任任何客户端提交的重定向 URL。应使用白名单机制，严格限制可跳转的域名和路径。如果业务需要动态跳转，应在服务端进行域名校验，或者提示用户点击二次确认页面后再跳转。
  • 实战启发：遇到包含 url、redirect、target 等参数的接口，应优先尝试构造外部链接测试是否发生跳转。在测试失败时，可结合源码审计分析校验逻辑，寻找绕过方法（如使用 //evil.com 或 @evil.com 的解析漏洞）。
