【Pikachu】Web-XSS-反射型XSS(post) Writeup

操作者：何芊宏 | 操作日期：2026.9.27 | 分类：Pikachu | 标签：Pikachu, Web, XSS, 反射型XSS, POST型注入

1. 题目信息

  • 平台：Pikachu 漏洞练习平台
  • 分类：Web - Cross-Site Scripting (XSS)
  • 题目名称：反射型xss(post)
  • 环境：Burp Suite 社区版自带浏览器，先登录后测试。
  • 目标：在 POST 请求参数中注入恶意 JS 代码，并成功执行弹窗。

2. 解题思路与知识点

漏洞原理：

与 GET 型类似，后端未对用户输入进行过滤和转义，直接将其输出到页面。区别在于数据的传输方式变成了 POST 请求，参数藏在请求体（Request Body）中，无法通过修改 URL 来直接注入。

【核心对比】GET 型与 POST 型 XSS 的差异：
  • GET 型：数据在 URL 中，通过修改地址栏参数即可测试。
  • POST 型：数据在请求体中，必须使用 Burp Suite 抓包，拦截 POST 请求并修改请求体中的参数。

3. 操作步骤

第一步：登录并探测注入点

操作： 在bp自带浏览器访问靶场，使用 admin/123456 进行登录。登录成功后，页面出现“Which NBA player do you like?”输入框。

分析： 该输入框是一个 POST 表单，提交后的 URL 变成了 xss_reflected_post.php，确认是 POST 方式的反射型注入点。

第二步：抓包与 Repeater 注入

操作： 在输入框输入 test 并提交，Burp 拦截到 POST 请求。

请求体： message=test&submit=submit

注入操作： 右键发送到 Repeater，将请求体修改为：message=<script>alert(1)</script>&submit=submit，点击 Send。

第三步：验证弹窗

坑点发现： 在 Repeater 中点击 Render 标签，并未弹出对话框。这是因为 Burp Suite 的渲染沙箱会主动拦截 JavaScript 的执行。

绕过验证： 在 Response 区域右键，选择 Open response in browser，复制临时 URL，粘贴到 Burp 自带浏览器中打开。

回显结果： 浏览器成功弹出 127.0.0.1 显示 1，证明 Payload 被执行，漏洞利用成功。

4. 踩坑记录与复盘

  • 坑1：Burp Repeater 的 Render 功能不执行 JS。出于安全考虑，Burp 内置的响应渲染器屏蔽了脚本执行。实战中必须使用 Open response in browser 或手动构造 HTML 文件在浏览器打开，才能触发弹窗。
  • 坑2：登录状态维持。从普通浏览器切换到 Burp 自带浏览器时，需重新使用 admin/123456 登录，否则无法进入注入页面。

5. 知识总结

  • POST 型 XSS 的利用场景：常见于评论提交、资料修改等表单交互处。攻击者需要构造一个自动提交的 POST 表单（如利用 JS 自动提交）或诱导受害者点击恶意链接，才能完成攻击。
  • Burp 的实用功能：熟练使用 Repeater 改包以及 Open response in browser 验证渲染结果，是渗透测试中必不可少的技能。
  • 防御建议：无论 GET 还是 POST，服务端都应一视同仁地进行输入过滤和输出 HTML 实体转义。
