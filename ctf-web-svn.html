【CTFHub】Web-SVN泄露 Writeup

操作者：何芊宏 | 操作日期：2026.9.20 | 分类：CTF | 标签：CTFHub, Web, 信息泄露, SVN, SQLite

1. 题目信息

  • 平台：CTFHub
  • 分类：Web - 信息泄露 / SVN泄露
  • 题目名称：SVN泄露
  • 提示：开发人员使用 SVN 进行版本控制并直接部署到线上，导致 .svn 文件夹泄露。Flag 在服务端旧版本的源代码中。

2. 解题思路

题目提示非常明确，源码中遗留了 .svn 文件夹。SVN 的 .svn 目录包含记录所有文件路径的数据库文件 wc.db，以及存储原始文件内容的 pristine 文件夹。我们只需下载 wc.db 数据库，从中找到目标文件的哈希值，然后拼凑出服务器上的物理路径，即可下载到被删除的 Flag 文件。

3. 操作步骤

第一步：环境探测与工具受挫

开启 CTFHub 环境后，我首先想去 GitHub 下载 svnExploit 工具，结果发现该仓库已经 404（被原作者删除了）。导师及时给出备用方案：手动下载数据库，并用可视化工具查看。我下载并安装了 DB Browser for SQLite 软件。

第二步：获取核心数据库 wc.db

在浏览器直接访问目标 URL 拼接上 /.svn/wc.db，成功下载了一个大小为 120.00 KB 的 wc.db 文件。

第三步：使用数据库软件寻宝

打开 DB Browser for SQLite，加载 wc.db。点击“浏览数据”，选择 NODES 表，看到了一条非常显眼的记录：flag_3008724284.txt。我满心欢喜地去浏览器访问 http://.../flag_3008724284.txt，结果却是一个无情的 404 Not Found。

【踩坑记录】：明明数据库里有这个文件，为什么访问不到？查看表字段发现，这个文件的 checksum（哈希值）是 NULL。原来文件在工作区被删除了，所以直接访问 404。

第四步：绝境逢生，寻找丢失的哈希值

在导师的指导下，我点开了左侧的 PRISTINE（纯净物）表。这里记录着所有文件的原始内容。我按照文件大小筛选，发现第 2 行的文件大小为 33 字节（恰好是一个 Flag 的长度），它的哈希值是：$sha1$e80581278f907c367fac511d3efff2bf191c6c52。

第五步：手工拼凑终极链接

SVN 存储文件有固定的路径规则：.svn/pristine/ + 哈希前两位 + / + 剩余字符 + .svn-base。我尝试拼接并访问，结果又报错了 404。经过导师指点，原来前面的 $sha1$ 只是标识算法，拼接时不需要带上它。

最终构造正确的 URL：

http://challenge-4a4f2a423219dc50.sandbox.ctfhub.com:10800/.svn/pristine/e8/0581278f907c367fac511d3efff2bf191c6c52.svn-base

第六步：成功获取 Flag

浏览器访问这个 URL 后，直接下载了一个文件。用记事本打开下载的文件，里面赫然写着：

ctfhub{8228b6af601bc15221e3fd6e}

提交至 CTFHub，顺利通关！

4. 踩坑记录与复盘

  • 工具失效不慌：本次原本准备用自动化脚本 svnExploit，但 GitHub 仓库 404。这说明安全工具更迭很快，不能过度依赖，掌握手动下载 wc.db 并分析的方法是根本。
  • 理解 SVN 的删除逻辑：在 NODES 表看到文件，直接访问却 404，是因为文件在服务器被删除了。此时它的“实体”被藏在了 PRISTINE 表里，必须去那里找哈希。
  • URL 拼接的坑：拿到哈希值后，$sha1$ 只是前缀，实际文件名不包含它。去掉前缀并按照“前两位作目录”的规则拼接，是成功的关键。

5. 知识总结

  • SVN 泄露原理：SVN 为了追踪版本，会在工作目录生成 .svn 文件夹。若部署时未清理，攻击者可直接下载其内容。
  • 核心文件：
    • .svn/wc.db：SQLite 数据库，记录文件路径（NODES 表）和原始文件哈希（PRISTINE 表）。
    • .svn/pristine/：存放所有文件原始内容的目录，文件名即文件哈希。
  • 物理路径映射：/.svn/pristine/ + 哈希前两位 + / + 哈希剩余 + .svn-base。
