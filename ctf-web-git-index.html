【CTFHub】Web-Git泄露(Index) Writeup

操作者：何芊宏 | 操作日期：2026.9.20 | 分类：CTF | 标签：CTFHub, Web, 信息泄露, Git, Python

1. 题目信息

  • 平台：CTFHub
  • 分类：Web - 信息泄露 / Git泄露
  • 题目名称：Index
  • 提示：开发人员可能把文件添加进暂存区（Index），但未提交（commit），随后工作区文件被删，需要从暂存区中恢复。

2. 解题思路

题目名为“Index”（索引/暂存区）。在 Git 的工作流中，修改文件后执行 git add，文件会进入暂存区（Index），随后才会执行 git commit 正式提交。如果开发人员只执行了 add 却没来得及 commit，即便工作区的文件后来被删除了，它的“灵魂”（元数据）依然保留在 .git 的 Index 中。我们只需下载完整的源码，然后用对应的 Git 命令把暂存区的东西“掏出来”。

3. 操作步骤

第一步：环境清理与开题

重启电脑后，我打开 VS Code，确认 Python、Git 和 githacker 依然可用，无需重新安装。开启 CTFHub 环境，拿到目标 URL：http://challenge-bb44f6d692b7e70f.sandbox.ctfhub.com:10800。

第二步：下载完整仓库

吸取了前两题的经验，直接使用 githacker 命令（避免使用 python GitHack.py 导致丢失历史记录），并在终端执行：

githacker --url http://challenge-bb44f6d692b7e70f.sandbox.ctfhub.com:10800/.git/ --output ./source_code_index

【踩坑记录】：命令执行后，终端中间爆出一大段红色的 ERROR 字眼（ERROR Cloning into ...）。第一反应是“是不是路径写错了要重来？”但仔细看红字下面，紧跟着绿色的 done. 和 INFO 1 / 1 were exploited successfully。经导师讲解，那行红色的字只是工具在克隆时的一个小牢骚（路径转义问题），实际文件已经成功下载了。于是我们继续往下走。

第三步：进入目录，查看状态

在左侧资源管理器中，找到新生成的 source_code_index 文件夹，点开里面长串字母数字的文件夹 f83626cf07f827990190b1da20efc343，右键选择“在集成终端中打开”。

在新终端里输入：

git status

终端显示：Changes not staged for commit: modified: 223682594213022.txt, 50x.html, index.html。这说明除了网页基础文件被修改过外，还有一个随机数字命名的 .txt 文件被修改过，它就是我们要找的目标。

第四步：掏出暂存区里的文件

这道题的核心命令不是 git reset，也不是 git stash，而是专门针对 Index 的恢复命令：

git checkout-index -a

执行完这条命令后，终端没有抛出任何报错。但是，左侧的资源管理器里，原本那个随机命名的 223682594213022.txt 文件赫然出现！

第五步：获取 Flag

双击打开 223682594213022.txt，里面写着：

ctfhub{8ed7c371315ea44802e99703}

复制并提交到 CTFHub，成功拿下 Index 关卡！

4. 踩坑记录与复盘

  • 把“成功警告”当成“报错”：终端输出红字 ERROR 时不要慌，看它后面有没有 done 或者 successfully 之类的绿字。我们需要的是结果，过程中的怨言不影响。

    • 5. 知识总结

    • Git Index (暂存区) 概念：它是 Git 三棵树（工作区、暂存区、版本库）中间的重要一环。如果只 git add 没有 git commit，文件就会一直挂在 Index 里。
    • 核心命令：
      • git status：查看当前工作区和暂存区的状态，能快速发现被删除或修改的隐蔽文件。
      • git checkout-index -a：从暂存区（Index）中将所有（-a）文件检出到当前工作目录，即便它们被物理删除了也能恢复出来。

    6. 三种 Git 泄露比较

    为了更好地理清思路，我将这三道 CTF 题目中出现的 Git 泄露类型进行了横向对比，它们分别对应了 Git 工作流中的不同阶段：

    泄露类型 开发人员做了什么（痛点） 破局核心命令 通俗比喻
    Log 写了 Flag，正常提交（commit），后来又把它删掉了（remove flag）。 git log
    git reset --hard HEAD^    		 时光倒流
    Flag 曾存在过，被删了。用时光机倒回到删除前的历史版本。
    Stash 写了 Flag，不想提交，把它塞进了草稿箱（git stash），后来也没拿出来。 git stash list
    git stash pop    		 掏抽屉
    Flag 没正式提交，只是被藏在了暂存区。我们把抽屉拉开倒出来。
    Index 写了 Flag 并执行了 git add 放到索引区，但没提交，随后工作区文件也被删了。 git status
    git checkout-index -a    		 恢复索引
    文件物理上没了，但登记簿上还有。我们照着索引簿把它重新恢复出来。
