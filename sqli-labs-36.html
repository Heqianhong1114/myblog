【SQLi-Labs】Less-36 Bypass MySQL Real Escape String Writeup

操作者：何芊宏 | 操作日期：2026.10.27 | 分类：CTF | 标签：SQLi-Labs, Web, SQL注入, 宽字节注入, 源码审计

1. 题目信息

  • 平台：SQLi-Labs (本地 phpStudy 环境)
  • 分类：Web - SQL注入
  • 题目名称：Less-36 (GET - Bypass MySQL Real Escape String)
  • 提示：页面回显转义后的十六进制字节流。采用了高级转义函数，但数据库连接配置存在缺陷。

2. 核心原理：防御函数与字符集配置的错位

本关卡使用了 mysql_real_escape_string() 函数进行防御。与 addslashes() 相比，它更先进，因为它在转义前会尝试读取当前的连接字符集，以防止宽字节注入。

漏洞成因：

  1. 开发者通常使用 mysql_query("SET NAMES gbk") 来设置字符集，而不是使用 mysql_set_charset('gbk')。
  2. 这导致 mysql_real_escape_string() 在转义时，误以为当前环境是安全的默认字符集，于是照常将单引号转义为 \'（十六进制 0x5C 0x27）。
  3. 但当 SQL 语句发送给 MySQL 引擎执行时，引擎按 GBK 编码解析，将输入的高位字节 0xDF 与转义符 0x5C 组合成了一个汉字，导致单引号 0x27 成功逃逸。

3. 操作步骤与解析

第一步：验证宽字节与转义

输入 URL：?id=1%df'

回显现象：页面底部 Hex 提示为 31 df 5c 27，且 SQL 语法报错中出现了由 df 5c 拼成的汉字（如“運”），证明单引号成功逃逸。

第二步：联合查询爆库名

输入 URL：?id=-1%df' union select 1,2,database()-- -

回显现象：页面第 2 列回显 security。

第三步：联合查询脱库

输入 URL：?id=-1%df' union select 1,2,group_concat(username,0x3a,password) from users-- -

回显现象：页面直接爆出所有账号密码（如 Dumb:Dumb、admin:p@ssw0rd 等）。

4. 踩坑记录与复盘

  • 思维定势：看到“Real Escape String”不要以为无懈可击。在 PHP 5.4 及更早版本中，字符集设置方式的不规范（如 SET NAMES）极易导致该函数失效。
  • 原始字节传递：在浏览器地址栏直接输入 %df。切忌使用二次 URL 编码工具，否则原始字节无法到达底层。

5. 知识点总结

  • 防御失效场景：深入理解 PHP 转义函数与 MySQL 字符集解析机制之间的“信息差”。
  • 宽字节注入通用性：只要数据库连接使用了 GBK 等双字节字符集，且输入未经过严格的正则替换或白名单校验，宽字节注入手法基本通杀。
