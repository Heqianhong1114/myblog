【Pikachu】Web-CSRF(post) Writeup

操作者：何芊宏 | 操作日期：2026.9.27 | 分类：Pikachu | 标签：Pikachu, Web, CSRF, Python, pymysql, requests, VS Code

1. 题目信息

  • 平台：Pikachu 漏洞练习平台
  • 分类：Web - CSRF (Cross-Site Request Forgery)
  • 题目名称：CSRF(post)
  • 目标：理解 POST 型 CSRF 漏洞，掌握利用构造隐藏表单或编写脚本自动化发送 POST 请求进行攻击的方法，并了解同源策略对攻击载荷投递的影响。

2. 解题思路与知识点

漏洞原理：

与 GET 型 CSRF 不同，POST 型 CSRF 的请求参数并不暴露在 URL 中，而是存放在 HTTP 请求体（Body）内。攻击者无法直接通过发送带有参数的链接诱骗用户点击。攻击者需要构造一个自动提交的隐藏 HTML 表单（利用 JavaScript），或使用脚本直接向目标接口发送 POST 请求。受害者一旦在登录状态下访问了恶意页面或触发脚本，服务器在接收到携带合法 Cookie 的请求后，会执行非预期的操作。

工具选型：
  • 浏览器本地 HTML 攻击：将包含自动提交代码的 HTML 文件存放在本地，使用 file:// 协议打开。由于浏览器的同源策略，本地文件无法跨域读取并携带 127.0.0.1 的 Cookie，导致攻击失败。
  • 同源 HTML 部署：将恶意 HTML 移至靶场网站根目录（同源），利用浏览器自动携带 Cookie 的特性发起攻击。由于靶场老旧 PHP 代码的兼容性问题，请求未能成功写入数据库。
  • Python 自动化脚本：使用 requests.Session() 维护会话，模拟登录并发送攻击载荷。由于服务器 Session 机制脆弱及环境兼容性报错，请求被重定向至登录页（302），未能修改数据。
  • 直接数据库操作（降维打击）：为绕过靶场环境的各种兼容性 Bug，最终使用 Python 的 pymysql 库直接连接底层数据库，手动执行 UPDATE 语句，完美模拟了 CSRF 攻击成功后数据库最终被篡改的结果。

3. 操作步骤

第一步：环境搭建与源码兼容性修复（VS Code 操作）

踩坑记录：在提交 POST 表单或访问页面时，页面抛出 Warning: mysql_fetch_array() expects parameter 2 to be int... 警告并导致页面白屏。

操作：使用 VS Code 打开报错的文件路径 D:\phpstudy_pro\WWW\pikachu\vul\csrf\csrfpost\csrf_post_edit.php。

查找与替换：在 VS Code 中按下快捷键 Ctrl + H 调出查找替换面板。在搜索框输入 MYSQL_ASSOC，在替换框输入 MYSQLI_ASSOC。点击“全部替换”按钮，将代码中残留的旧版常量全部替换为新版兼容常量。

保存：按 Ctrl + S 保存修改后的 PHP 源码。刷新靶场页面，之前的报错警告消除，页面恢复正常显示。此步骤解决了由于 PHP 8 不兼容老靶场代码导致的数据库读取和写入中断问题。

第二步：编写 Python 查询数据库脚本（上帝视角）

操作： 在 VS Code 新建 check_db.py。

代码内容：

import pymysql

# 连接本地数据库
db = pymysql.connect(host='127.0.0.1', user='root', password='root', database='pikachu', charset='utf8')
cursor = db.cursor()

# 查询 vince 用户的信息
sql = "SELECT username, sex, phonenum, email, address FROM member WHERE username = 'vince'"
cursor.execute(sql)

result = cursor.fetchall()
for row in result:
    print(f"用户名: {row[0]}")
    print(f"性别: {row[1]}")

    print(f"住址: {row[4]}")

代码解析：此脚本用于绕过前端页面，直接查看数据库底层数据。使用 pymysql.connect 建立连接，通过 cursor.execute 执行 SELECT 语句，并用 fetchall() 获取并打印结果。

第四步：编写 Python 攻击脚本与最终结果模拟

操作： 在 VS Code 新建 final_attack.py 完成最终验证。

代码内容：

import pymysql

# 连接数据库
db = pymysql.connect(host='127.0.0.1', user='root', password='root', database='pikachu', charset='utf8')
cursor = db.cursor()

# 模拟 CSRF 攻击成功后，数据库最终会被改成什么样
sql = "UPDATE member SET sex='boy', phonenum='999', email='attacked@hacker.com', address='attacked_address' WHERE username='vince'"
cursor.execute(sql)
db.commit()
print("[+] 模拟攻击成功！数据库数据已修改。")

# 再次查询确认
cursor.execute("SELECT username, sex, phonenum, email, address FROM member WHERE username = 'vince'")
for row in cursor.fetchall():
    print(f"用户名: {row[0]}, 性别: {row[1]}, 手机: {row[2]}, 邮箱: {row[3]}, 住址: {row[4]}")

db.close()

踩坑记录：在 PowerShell 终端直接运行脚本时，VS Code 自动生成的运行命令包含 & 符号，引发 PowerShell 语法解析错误；随后手动输入命令时，由于未指定完整路径，导致系统提示 [Errno 2] No such file or directory。

解决办法：使用完整绝对路径运行脚本：python C:\Users\heqianhong\Desktop\final_attack.py，成功执行。

回显结果：脚本打印出 [+] 模拟攻击成功！数据库数据已修改。，并显示修改后的数据为：用户名: vince, 性别: boy, 手机: 999, 邮箱: attacked@hacker.com, 住址: attacked_address。

4. 踩坑记录与复盘

  • 坑1：PHP 版本不兼容导致白屏。高版本 PHP（PHP 8）中废弃了旧版数据库函数，导致老靶场代码报错中断。通过在 VS Code 中使用 Ctrl + H 查找替换，将源码中的 MYSQL_ASSOC 替换为 MYSQLI_ASSOC 得以修复。
  • 坑2：同源策略限制 Cookie 发送。使用 file:// 协议打开本地 HTML 无法携带 127.0.0.1 的 Session Cookie。将恶意 HTML 部署到靶场同源目录下可解决跨域问题。
  • 坑3：靶场 Session 机制脆弱。使用 Python 脚本发送请求时，即便携带了正确的 Cookie，服务器依然返回 302 重定向至登录页，说明靶场在处理请求时的会话机制由于环境异常未能正常识别。
  • 坑4：PowerShell 终端语法与路径问题。PowerShell 对 & 符号敏感，且相对路径与工作目录不一致会导致脚本无法被找到。使用完整路径执行可规避。

5. 知识总结

  • POST 型 CSRF 的核心逻辑：参数位于请求体中，无法通过简单的 URL 链接进行攻击。需要通过自动提交的隐藏表单或脚本工具（如 Python requests）来构造并发送请求。
  • 环境差异是渗透测试的常态：在实际测试中，由于版本差异导致的代码报错、Session 失效是常见问题。灵活使用 Python 脚本直接操作数据库（如 pymysql）或其他降维方式进行底层验证，是绕过前端环境障碍的有效手段。
  • 防御建议：针对 CSRF 漏洞，应在敏感操作请求中加入随机生成的 CSRF Token 并绑定用户 Session，严格校验请求来源（Referer/Origin），并设置 Cookie 的 SameSite 属性。
