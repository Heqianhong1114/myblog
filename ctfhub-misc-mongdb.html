【CTFHub】MongoDB流量 Writeup

操作者：何芊宏 | 操作日期：2026.10.21 | 分类：CTF | 标签：CTFHub, 流量分析, Wireshark, MongoDB, BSON

1. 题目信息

  • 平台：CTFHub
  • 分类：流量分析 - 数据库类流量
  • 题目名称：MongoDB流量
  • 附件：包含一个约 174KB 的 mongodb.pcap 文件

2. 解题思路

MongoDB 默认端口为 27017，其底层通信使用 BSON（Binary JSON）格式，这是一种类似 JSON 的二进制序列化格式。与 Redis 的纯文本协议不同，BSON 包含大量嵌套结构和数据类型标识。在流量分析中，Flag 通常会作为某个文档（Document）中的字段值被查询或返回。解题核心在于利用 Wireshark 的底层字节流搜索功能定位关键字，并解析其对应的 BSON 数据结构以提取完整数据。

3. 操作步骤

第一步：协议过滤与初步观察

使用 Wireshark 打开附件。过滤出 SSH 和 TCP 握手包后，观察到大量基于 MONGO 协议的数据包。应用显示过滤器 mongo，发现前期的交互包（如第 14、17、22 号包）主要包含 ismaster、connectionStatus 等客户端与服务器的握手及状态探测指令，未发现有效业务数据。

第二步：调整搜索策略与定位

为快速定位 Flag，按下 Ctrl + F 调出搜索框。首次尝试在“分组列表”模式下搜索 ctfhub，虽然定位到了相关数据包，但解析出的内容为 ctfhub.$cmd，表明该字符串仅代表数据库名称，而非 Flag 本体。

随后调整搜索策略：
1. 将搜索模式由“分组列表”切换为 “分组字节流” (Packet bytes)，使 Wireshark 深入到底层十六进制及 ASCII 数据中进行匹配。
2. 将搜索关键字由 ctfhub 修改为 ctfhub{，利用 Flag 固定格式（包含左大括号）过滤掉数据库名的干扰。

第三步：解析 BSON 结构与提取结果

执行搜索后，成功跳转至第 620 号包（Response : Reply）。观察中间下方的详情面板，依次展开：
Mongo Wire Protocol -> documents -> Document -> Elements -> Element: flag。
在 Element: flag 节点下，发现 Value 字段包含完整的明文字符串：ctfhub{5f284ecc279d2cbd1af258bb53c7a5f6}。同时，右侧的十六进制/ASCII 面板也直观地展示了该明文。

4. 踩坑记录与复盘

  • Wireshark 搜索模式的差异：“分组列表”仅搜索界面上展示的 Info 摘要信息，无法命中隐藏在深层数据体中的内容；“分组字节流”则直接对数据的原始字节进行检索。在遇到二进制协议或深层嵌套结构时，必须使用“分组字节流”模式。
  • 关键字前缀的干扰：直接搜索 ctfhub 容易受到环境变量、数据库名（ctfhub.$cmd）等干扰项的误导。结合格式特征（如 ctfhub{、flag{）进行检索，能够极大提高定位的准确率。

5. 知识总结

  • MongoDB BSON 协议：BSON 是一种类 JSON 的二进制存储格式。在 Wireshark 的解析树中，数据通常表现为 Document（文档）包含多个 Elements（元素），每个元素都有特定的类型标识（如 Type: String (0x02) 表示该字段为字符串），这种结构化的存储方式使得数据在未加密时极易被还原。
  • 流量分析中的降维打击（全局搜索）：在遇到解析树过于复杂、或者数据包数量庞大的情况下，放弃手动逐层展开，直接使用底层字节流搜索关键字（如 flag 格式前缀），是 CTF 流量分析中最快、最有效的实战技巧之一。
