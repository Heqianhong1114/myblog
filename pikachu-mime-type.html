【Pikachu】Web-不安全的文件上传-MIME type Writeup

操作者：何芊宏 | 操作日期：2026.9.28 | 分类：Pikachu | 标签：Pikachu, Web, 文件上传, MIME类型绕过, Burp Suite

1. 题目信息

  • 平台：Pikachu 漏洞练习平台
  • 分类：Web - Unsafe Fileupload (服务端检查)
  • 题目名称：MIME type
  • 目标：利用后端仅通过 HTTP 请求头中的 Content-Type 来校验文件类型的缺陷，通过篡改该字段为图片类型，绕过限制上传 PHP 文件并成功执行。

2. 解题思路与知识点

漏洞原理：

在文件上传中，HTTP 请求会使用 multipart/form-data 格式。对于每个文件，请求体（Body）中会包含一个 Content-Type 字段（例如图片为 image/jpeg，PDF 为 application/pdf）。部分开发者为了省事，会直接在 PHP 后端读取 $_FILES['file']['type'] 来判断文件合法性。但客户端提交的 Content-Type 完全由攻击者可控，我们可以通过抓包工具将其修改为合法的图片类型。

重点概念区分：顶层请求头与文件分块头
  • 顶层请求头：声明当前请求是 multipart/form-data，并指定分隔符。此字段不可修改，否则服务器无法解析请求。
  • 文件分块头：在分隔符之后，单独描述上传文件的信息（包括 filename 和 Content-Type）。这里的 Content-Type 才是我们需要修改的。

3. 操作步骤

第一步：直接上传测试与后端拦截分析

操作： 在浏览器中选择之前创建的 shell.php，点击“开始上传”。

回显： 页面提示“上传的图片只能是jpg,jpeg,png格式的！”。

原理分析： 这说明前端没有校验，请求成功发送到了后端。后端读取了 PHP 文件默认的 Content-Type: application/octet-stream，判定不是图片格式，从而直接阻断。

第二步：使用 Burp 篡改 MIME 类型

操作： 确保 Burp Suite 开启拦截。在浏览器中再次选中 shell.php，点击上传。

篡改请求： 在 Burp 拦截到的 POST 请求中，修改以下两处内容：

  1. 确保文件声明部分为： Content-Disposition: form-data; name="uploadfile"; filename="shell.php"
  2. 将该文件分块头下方的类型标识修改为： Content-Type: image/jpeg （必须将原来的 application/octet-stream 改掉）
  3. 将请求体中的二进制数据（如果有）替换为 PHP 代码： <?php echo "pikachu_upload_success"; ?>

代码组成详细解释：

  • Content-Disposition: form-data; name="uploadfile"; filename="shell.php"：描述这是一个表单字段，字段名为 uploadfile，文件名被强制指定为 shell.php。
  • Content-Type: image/jpeg：这是 HTTP 协议中用于描述文件类型的头部字段。后端代码如果不检查文件实际内容，只检查这个字段，就会被欺骗。
  • <?php echo "pikachu_upload_success"; ?>：PHP 代码实体，被包含在请求体中，服务器解析并执行后，页面输出对应字符串。

回显特征： 点击 Forward 放行后，页面提示“上传成功”，文件保存路径为：uploads/shell.php。

第三步：访问 Shell 验证代码执行

操作： 在浏览器地址栏输入 http://127.0.0.1/pikachu/vul/unsafeupload/uploads/shell.php。

回显： 页面输出 pikachu_upload_success。证明文件不仅被成功保存，且其中的 PHP 代码被服务器解析执行。

4. 踩坑记录与复盘

  • 坑1：直接上传 PHP 文件被后端拦截。尝试直接在浏览器中选择 shell.php 上传，被后端 MIME 类型校验拦截。说明后台使用了 $_FILES['file']['type'] 进行白名单校验，只允许 image/jpeg、image/png 等类型。
    解决办法： 改用 Burp Suite 抓包，找到文件分块头的 Content-Type 字段，直接修改为 image/jpeg，伪造文件 MIME 类型以欺骗后端。
  • 坑2：误将顶层请求头修改为图片类型。初次修改时，由于没有注意 HTTP 请求结构，不小心将顶层的 Content-Type: multipart/form-data; boundary=... 改成了 Content-Type: image/jpeg，导致请求解析失败。
    原因排查： 顶层请求头是用于告诉服务器“请求体是分块的，分块符是什么”，必须保持 multipart/form-data 不变。真正需要欺骗后端的是位于 Content-Disposition 下方、描述具体文件类型的 Content-Type。

5. 知识总结

  • 漏洞本质：MIME 类型绕过是“信任边界失效”的典型表现。任何来自客户端的 HTTP 头信息（包括 Content-Type）都是可以被篡改的，不能作为安全校验的依据。
  • 防御措施：在服务端，不能信任 HTTP 请求头中的 MIME 类型。应该使用 PHP 的 finfo_file() 函数读取文件的真实 MIME 类型，或者使用 getimagesize() 检查文件的实际内容。此外，上传目录必须设置禁止执行 PHP 脚本（如通过 Nginx 配置 location ~ \.php$ { return 403; }）。
  • 实战启发：在文件上传点测试中，首先应检查后端是否依赖 HTTP 头（MIME Type）来判断类型。若可以绕过，再进一步测试文件内容是否会被检查（对应下一关 getimagesize）。
